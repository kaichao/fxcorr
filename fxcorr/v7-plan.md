# fxcorr V7 计划（草稿）

> **草稿**（2026-09-28 拟于 V6 收尾时）——**v7 正式开工时再讨论定稿**，本文档目前的用途是让 v6
> 交出来的东西有处可放、让 v7 的起点清楚。分工与 v1–v6 一致：容量与瓶颈在 `data-volume.md`，
> 数据规范在 `data-spec.md`，命令行在 `usage.md`，V6 的全部结论在 `v6-plan.md`。

## V7 的起点（V6 交出来的状态）

**工具侧已经闭环**：三个程序（`fxcorr-f` / `fxcorr-x` / `fxcorr-sim`）功能完整，判据按
单测 → 合成 → 真机三层铺开；分片（`(batch, ds 组)`）与两级 `merge` 已落地并验证；S3 用 4 站 ×
8 ds × 20 个连续 batch 把单机全链跑通（`v6-plan.md` 验收表）。

**没兑现的是"部署"**：`v6-plan.md` 的「多节点部署形态」一章——计算单元 = `(batch, ds 组)`、
`fengine` 落 tmpfs、`FXCORR_WORKDIR` 必须全局共享、只有 `.part` 与 SWIN 出节点——**只有设计，
一次都没在真跨节点环境上跑过**。编排本身在 **scalebox（另一个仓库）**，本仓库交付的是规范与
程序内接口。**"数百节点并行同一个实验"这套设计的第一次真实检验还没发生。**

**两个硬约束**（它们决定 v7 能做什么，不是"待办"而是外部条件）：

| 约束 | 卡住的事 |
|---|---|
| **真多节点环境** | 跨节点流量实测（S3 判据里唯一没测的那一格）、S5.4 的 `PCAL_*` 并发写、多节点部署联调 |
| **第二份真实观测** | S5.3 的四项（FILL_PATTERN / invalid 位的真实样本、filler 修正量形态、病态数据对拍基准、真实 `.calc` 的 `IM`/`FLAG FILENAME` 形态） |

## 候选方向

### A. 多节点部署联调（v6 欠下的那一半）

**做什么**：在 scalebox 里把 V6 的部署形态落地，然后**真跨节点跑一次**——按 `(batch, ds 组)`
分布、`fengine` 落各节点 tmpfs、`vis-parts/` 与 `vis/` 落共享盘、由实验级 `merge --experiment`
单点写 SWIN。要测的量照 `v6-plan.md` S3 的口径：端到端 wall time、**跨节点流量**、单节点磁盘
与 tmpfs 峰值、长稳。

**为什么值得**：这是 V6 主题（"规模与部署"）里唯一没验的一半；也是分片架构相对 mpifxcorr 的
核心主张（`fengine` **不出节点**）第一次被量化——S3 只在单机上比过 wall 与 CPU。

**前置**：多节点环境 + scalebox 仓库。**代价**：跨仓库协作，本仓库这边可能只需补接口。

### B. 性能（本仓库内可控，且有 S3 的实测指向）

**依据**：S3 的单机对照把话说得很清楚——**CPU 是唯一的真瓶颈**（fxcorr CPU 210 s vs
mpifxcorr 4276 s；而 `fengine` 走 tmpfs、磁盘不在这条路径上）。`data-volume.md` §6 的杠杆与
§8 的未验证项也全指向这里。

**三个候选，按性价比排**：

1. **单节点 TFLOPS 标定**——`data-volume` §3 里那个 "≈1.7 TFLOPS" 是公式粗估（未计内存带宽、
   OpenMP 效率、I/O 等待），而它决定"要多少节点才能追上实时"。做法就是 S3 那套跑法加计数器。
2. **按 ds 调度**（`data-volume` §6 杠杆 3 的落地）——fxcorr-sim 的多 ds 能力已具备（V5），
   缺的是让 f 任务按 ds 并行铺开而不是逐站串行；S3 已量到逐站串行会让整链比 mpifxcorr 还慢
   （235 s/batch），这是最直接的一刀。
3. **x 的流式化**（杠杆 5）——降内存 8×，但先要解决"`fengine` 磁盘不降"（§7.2），
   在 tmpfs 已够用的现状下收益有限。

### C. 功能边界

- **分片支持多相位中心 / pulsar binning**——S6.3 记的**有意边界**（现在是程序内报错退出）；
  要放开得先扩 `Visibility` 的单缓冲区假设（`data-spec` 5.9）。**需求驱动弱**，等真实场景。
- **cf16**——**条件触发，不是欠账**：触发条件已于 2026-09-28 改写为"分片后 tmpfs 容量成为
  单节点并行度上限"（`data-volume.md` §8 第 1 项；当前 60 GB 放得下 3 组，cf16 后是 7 组）。
  代价是**与 mpifxcorr 的逐位对拍失效**，所以触发前不动。

### D. 生产化

容器编排、监控接入（`difxmonitor` 与 DifxMessage 已在）、错误恢复与重试语义、运维手册。
docker 六镜像已建成（V2）。**与 A 同源**，单独立项偏薄，更适合作为 A 的副产品。

## 怎么选（草稿的判断，定稿时推翻也正常）

**关键分叉是"多节点环境能不能拿到"**：

- **能拿到 → 选 A**。它是 v6 的账，也是这套架构最值得被检验的地方；B 里的第 2 项（按 ds 调度）
  本就会在 A 的联调里被迫解决。
- **拿不到 → 选 B**。S3 已经把瓶颈指得很明白，且完全在本仓库内可做、可测、可回归；C 与 D
  在没有 A 的情形下都缺驱动力。

**无论选哪个，有一条前置**：`v6-plan.md` 末节列的 **S5.5**（`executeseconds` 与 `writedata`
判据的时间基准不一致，`getScanStartSec() != 0` 时静默不写盘）——**v7 若放开多 scan，必须先修
它**。当前 V1 边界（单 scan）挡着。
