## 1. V7 的位置

**V7 的主题是这两笔的合并**：**在目标集群上把 CPU 的多核算力真正用起来，并第一次跨节点
验证**。前者是 P1–P4，后者是 P5。

**明确不在 V7 范围**：DCU 加速、百节点级的 MPI vs scalebox 对照、数百节点的调度规模、

## 4. 数据与共享存储

### 4.1 预生成，不在计算节点上串接

**仿真数据一次性预生成、放 `/work2`，供 fxcorr 与 mpifxcorr 共用。** 理由两条，第一条是
决定性的：

1. **对照必须喂同一份数据**。要比两者的效率，两边必须读完全相同的 `raw`。边跑边生成的话，
   两边的 PRNG 流、时间轴、文件切割只要有一点不同，对照就不干净——而这类差异恰恰最难排查
   （V6 已经吃过一次"raw 与 batch 时间轴不符"的亏，见 `v6-plan.md` S3 的进行中说明）。
2. **预生成几乎不要钱**：轻量模式造数 **8.6 s / 79 GiB**（20 batch，`v6-plan.md:547`）。它按
   `f(seed, station, band)` 直接生成载荷、**不生成公共信号**（`v6-plan.md:146`），绕开了
   覆盖跨度那 85% 的白算。V6 S3 里造数 8.6 s、流水线 4945 s——造数不是瓶颈。

顺带一条：预生成也更接近真实形态——真实观测的 `raw` 是外部给的，不来自被测试的程序。

**做法**：造数在**计算节点**上跑（`srun`，不在登录节点跑重活），产物写
**`/public/home/cstu0036/fxcorr/`**——两个目录的 32 并发带宽相当（4.13 对 4.25 GB/s），但
`/public/home` 的配额是 `/work2` 的 16 倍，而长稳要 TB 级（见下表）；且 `/work2` 的文件系统
已用 90%，满盘既拖慢写入又有写满风险。`/work2` 留给工作区（脚本、日志、小产物）。

### 4.2 `/work2` 要多大

**基准量**：4 站 × 8 ds × 1.024 s = **4.21 GB / batch**
（131.6 MB/文件 × 32 个 (站, ds) 文件；`v6-plan.md:547` 记录的"79 GB"是 **GiB**、即 84.2 GB）。

**最关键的一条：容量需求与并行度无关。** 多节点并行是"不同节点跑不同 batch"，读的是**同一份
`raw` 的不同片段**，总量不随节点数增长。并行度只影响**带宽**（§4.3），不影响容量。

| 场景 | batch 数 | `raw` 容量 | 观测时长当量 |
|---|---|---|---|
| V6 S3 同规模 | 20 | **84 GB** | 20 s |
| P2/P3/P4 全部实验 | 同上，**反复用同一份** | **84 GB** | — |
| 4 TB 配额上限 | ~950 | 4.0 TB | **~16 分钟** |
| 40 TB 池子上限 | ~9500 | 40 TB | **~2.7 小时** |

**结论：4 TB 绰绰有余。** 初期最省的用法是**造 20 个 batch（84 GB，占配额 2%），此后所有
实验全部复用这一份**。

**不占 `/work2` 但要一起探的量**：`fengine` 落 `/dev/shm`（分片后 16.8 GB/组）。若 Slurm 限制
了内存、或 `/dev/shm` 实际小于 60 GB，这条假设要重算——**P1 前置建档的头一项**。

### 4.3 共享存储带宽

**先澄清一个口径**：`data-volume.md` §5.1 的 **4.11 GB/s 是"追上实时"的要求**（1.024 s 的数据
在 1.024 s 内处理完），**不是单节点测试用例的要求**。按 131.6 MB ÷ 1.024 s × 32 算，实时口径
正是 **4.11 GB/s**，与 §5.1 一致。

| 情形 | wall/batch | 读 `raw` 平均 | 峰值 |
|---|---|---|---|
| **P2：串行**（V6 S3 现状 235 s） | 235 s | **17.9 MB/s** | **128.5 MB/s**（单任务全速） |
| P3：并行 8× 加速 | 29 s | 143 MB/s | 577 MB/s |
| P3：并行 32× 加速（理想） | 7.3 s | 573 MB/s | **4.11 GB/s** |
| —— 追上实时 | 1.024 s | 4.11 GB/s | 4.11 GB/s |

**32 个 f 任务并行时峰值确实会摸到 ≈4.11 GB/s**（32 个任务同时发起读），但**平均速率由算力
决定**——目标机 30 核追不上实时（`data-volume.md` §5.1 的算力账），所以平均只有几百 MB/s。

**判据（2026-09-29 已用实测核对，见 §2.2）**：

| 阶段 | 带宽要求 | 实测 | 判定 |
|---|---|---|---|
| P2（串行） | ≥ 130 MB/s | 单流 **376 MB/s**（`/work2`）、359（`/public/home`） | ✓ 远超 |
| P3（并行） | 峰值 ≥ 4.11 GB/s | 32 并发 **4.13**（`/work2`）、**4.25**（`/public/home`） | ✓ **刚好接住，无余量** |

**所以存储不是瓶颈，但也没有富余**——32 个 f 任务全速并行的瞬时峰值正好被 4.2 GB/s 接住。
稳态下压力远小于峰值（平均速率由算力决定，追不上实时 → 只有几百 MB/s）。**这同时回答了两
件事**：P2 为什么可以先用串行（对存储几乎无要求），以及 P3 的并行度上限在哪里——**并行度不必
再往上加，32 已经是存储能接住的天花板**。

## 5. 对照：两个层次，别混

**"scalebox 的处理效率"实际要比的是 `fxcorr-f + fxcorr-x`**——scalebox 是编排层，不是计算
单元。对照的两侧：

| | 计算 | 数据 | 单节点内的并行单元 |
|---|---|---|---|
| 基准 | mpifxcorr（`run_bench.sh`） | 同一份 `raw` | 1 manager + N ds + 1 |
| 对照 | fxcorr（`run_batch.sh`） | 同一份 `raw` | **32 个 (站, ds) 任务** |

| 层次 | 在哪做 | 比的是什么 |
|---|---|---|
| **单节点内** | **P4**（1 个节点） | 谁在 30 核上跑得更快——**算法效率 + 调度效率**。两边都零跨节点通信，公平 |
| **跨节点** | P5（≥2 节点） | **网络 vs 本地存储**——mpifxcorr 每个 batch 要付 ≈65.8 GB/s 的 IB 交换，fxcorr 是 0 |

**P4 这个对照本身很有价值**：V6 S3 在 384 核的 difx 上测过（mpifxcorr NP=34、wall 120.6 s /
CPU 4276 s；fxcorr wall 80.7 s / CPU 210 s → **wall 0.67×、CPU 1/20**），**在 30 核目标机上
重做结论可能翻转**——mpifxcorr 是"一个 batch 摊到 34 进程"，fxcorr 是"32 个任务正好对上
30 核"；核少时前者先撞超订。

## 6. 要回答的问题

| | 问题 | 现状 | 为什么重要 |
|---|---|---|---|
| **Q1** | 30 核的**实测 TFLOPS** | 只有公式粗估（1.7 TFLOPS 需求 / 0.15~0.6 供给） | **决定 N**——"要几个节点才追上实时"全押在这个数上 |
| **Q2** | 30 核**怎么分配**最快 | 任务间串行，任务内 OpenMP（V3 P3） | 235 s/batch 的直接原因，**P3 的核心** |
| **Q3** | tmpfs 实际能放几组 `fengine` | 按 60 GB 假算是 3 组（分片后 16.8 GB/组） | 决定单节点并行度上限 |
| **Q4** | `/work2` 的实测带宽够不够 | 见 §4.3 | 低于它就加预取层，架构仍成立 |
| **Q5** | 跨节点流量是不是真的 ≈0 | 理论值 0（只出 KB 级 SWIN） | 分片架构相对 mpifxcorr 的**核心主张** |
| **Q6** | 单节点上 mpifxcorr 的内存峰值 | **未知**（V6 S3 只记了 wall 与 CPU） | 唯一能回答"目标节点装不装得下 mpifxcorr"的数据 |

## 7. 已知症结：串行调度（Q2 的靶子）

`run_batch.sh` 有**两处串行**，都是同步调用（无 `&`、无 `wait`）：

| 位置 | 现状 | 并行单元数（4 站 × 8 ds） |
|---|---|---|
| `run_batch.sh:271-280` | `for entry in "${DSTATION[@]}"; do fxc fxcorr-f ...; done` | **32 个 (站, ds) 任务串行** |
| `run_batch.sh:290-298` | `while [ "$g" -lt "$NGRP" ]; do fxc fxcorr-x ...; done` | **4 个 ds 组串行** |

**接近但不完全对齐**：目标节点 **30 核**对 4 站 × 8 ds 的 **32 个 f 任务**——差 2 个，全部铺开
时**轻微超订 6%**。最自然的并行粒度（任务级）与硬件规模基本对齐，**这是 P3 最值得先做的一
刀**；而"超订这 2 个的实际代价"本身就是 P3 要量的第一个点。

**但"32 个任务各占一核"未必最优**：V3 P3 已在任务内做了 OpenMP 并行（f 侧 Mode 副本 + 块序
归约、x 侧基线循环并行，逐位全等对拍通过），其加速比**受串行 I/O 限制**。于是存在一个真正的
设计选择——同一批 30 核，是都给任务级，还是留一部分给线程级（P3 的矩阵）。

## 8. P1：仿真数据生成

**前置：环境建档**（只读探测 + 一次构建，不产生大文件）

- `/dev/shm` 实际大小（假定的 60 GB 对不对）、本地盘类型与容量
- `/work2` 的文件系统类型、**实测读写带宽**（顺序大文件 + 多并发）
- **有无 MPI**（决定 P4 能不能在目标机上做）
- **有无 Apptainer/Singularity**（V2 建的是 Docker 镜像，Slurm 集群通常只跑前者——决定用
  容器还是本地构建）
- 依赖：`autotools` / `fftw` / `codifio` / OpenMP 运行时；`nproc` 在 Slurm 的 cgroup/affinity
  下返回什么（决定 P3 的并行度是自动取还是必须显式给）
- 代码分发方式：`/work2` 共享盘构建一次各节点共用 / 各节点本地构建 / 容器
- 订正 `v6-plan.md:234` 的实验环境规格（192 → 384 核）

**主体**

- 用 fxcorr-sim 的**轻量模式**造数（4 站 × 8 ds × **20 个连续 batch**，≈84 GB）→
  `/work2/cstu0036/fxcorr/raw`
- **造数与流水线分开计时**（V6 S3 口径：造数 8.6 s / 流水线 4945 s）

**判据（自检）**：文件数 = 4 站 × 8 ds × 20 batch = 640；总大小落在 84 GB ± 5%；同站两个 ds
的载荷互不相关（`test/multids/README.md` 的判据）；造数耗时落档。

**✅ 实测记录（2026-09-29，`f12r4n02`）**：640 个 vdif + 32 个软链，合计 **84,221,646,688 B
（84.2 GB）**，单文件 **131,596,288 B**——**与 V6 S3 逐项同值**；20 个 batch 全部
`n_subints=200 / subint_ns=5120000` = 1.024 s；`-p 30` 并行造数约 1 分钟（串行要 ~9 分钟）。
**判据全过。**

**✅ 各组数据量实测（2026-09-29，batch 1，全部落 `FXCORR_WORKDIR`、不设本地根）**：

| 目录 | 实测 | 对照 |
|---|---|---|
| `raw/`（20 batch 全量） | **79 GiB** | 单 batch 4.0 GB（32 个文件 × 131,596,288 B） |
| **`fengine/`（单 batch，整 32 个 (站,ds)）** | **63 GiB ≈ 67.4 GB** | **与 `data-volume.md` §5.1"不分片 67.4 GB"吻合** |
| `vis/` | 1.2 M | SWIN 1.1 MB + 4 个 PCAL |
| `vis-parts/` | 空（未分片） | |
| `product/` | 4.0 K | |
| `meta/` | 8.5 K | |

**扣住下一步的一条算术**：**ds 组数是 4，不是 8**——ds 组按频段重叠跨站切分（`run_batch.sh:214` 的并查集），V6 S0 的记录是"32 datastream / 96 baseline / **4 个 ds 组各 8 ds**"。所以：

```
按 (batch, ds 组) 为计算单元：  63 GiB ÷ 4 = 15.75 GiB ≈ 16.9 GB / 组
```

**与 `data-volume.md` §5.1 的"分片后单组 16.8 GB"一致** ✓。**62 GB 的 tmpfs 装得下单组，可放 3 组**——而**整 batch 的 67.4 GB 装不下**。这就是"计算单元 = `(batch, ds 组)`"（`v6-plan.md` 部署形态）的由来，也是 P3 要落地的。

**两个坑**（**都不是环境问题，是脚本在低版本 bash / 多 batch 下的行为**）：

1. **`-n > 1` 会强制改写运行参数**：`make_testdata.sh` 的多 batch 分支（`NBATCH > 1`）把
   `SUBINT NANOSECONDS` 改成 **128 ms**、`INT TIME` 改成 **0.256 s**，生成 `config/test-sim.input`
   并**优先使用它**——于是 batch 变成 **25.6 s、每文件 3.29 GB**，20 个就是 **2.1 TB**（远超预算；
   实测已写 174 GB 才发现）。而原始 `test_1.input`（difxcalc 产物）本来就是对的
   **5.12 ms / 1.024 s**。**`v6-plan.md` S3 记的那个"幂等跳过导致 batch 时长变化"是同一件事**，
   当时只是推断，这次留了实证。修法：**预先生成一份参数正确的 `test-sim.input`**，脚本会复用
   （`if [ ! -f "$CFG/test-sim.input" ]`）：
   ```bash
   sed -e 's/^SUBINT NANOSECONDS:.*$/SUBINT NANOSECONDS: 5120000/' \
       -e 's/^INT TIME (SEC):.*$/INT TIME (SEC):     1.024/' \

   ```
2. **bash < 4.4 的空数组展开**：`make_testdata.sh:452` 的 `${TONES[*]}` 在"无 tone"（空数组）

   测试机是 5.x 所以从没暴露。**已修**（加 `:-`；`${ENVS[*]}` 一处同样处理）。

## 9. P2：串行 baseline

**用现状跑**：单线程 `run_batch.sh`，全链 f → x → merge → SWIN。

**为什么先串行**——它不只是"把功能跑起来"，还白送三样东西：

1. **并行化的分母**：没有它，"快了 N 倍"无从谈起；
2. **对共享存储几乎无要求**（峰值只有单任务的 128.5 MB/s），**把功能问题与存储问题彻底
   解耦**——依赖不齐、构建不过这类事会在存储压力最小的时候暴露；
3. **能预测 P3 需要多少带宽**：串行 wall 直接给出平均读速率（§4.3 那张表）。

**判据（自检）**：

- **SWIN 与 V6 S3 基准逐字节相同**（`cmp_swin.py`，是回归门禁）
- 串行 wall 落档；**与 V6 S3 的 235 s/batch 对照**（同规模，可直接比）
- 单任务内存峰值、`fengine` 的 tmpfs 峰值、`/work2` 实际读速率落档

**✅ 实测记录（2026-09-29，`f12r4n02`，batch 1）**：

| 项 | 目标机实测 | 对比 V6 S3（`ssh difx`，384 核） |
|---|---|---|
| **单 batch wall** | **14 分 59 秒（899 s）** | **235 s/batch** → **慢 3.8×** |
| SWIN | `DIFX_61037_024611.s0000.b0000` = **1,124,352 B** | **同值** ✓ |

## 10. P3：多核优化（V7 核心）

**要回答 Q2**：30 核怎么分。两条并行线，**任务级 × 线程级**：

| 线 | 在哪 | 现状 |
|---|---|---|
| **任务级**（多进程） | `run_batch.sh` 加并行度参数 | **串行**——`for` 循环同步调用 |
| **线程级**（OpenMP） | 程序内，`OMP_NUM_THREADS` | 已具备（V3 P3），效率未标定 |

**实验矩阵**：

**基准取 24 核，不用满 30**（2026-09-29 定）：留 6 核余量给 I/O、系统与 Slurm 自身开销。
首次测试求稳——**目标不是"把核用满"，是"核效率最高"**，而两者未必是同一个点。

| 方案 | 任务并行度 | 每任务线程 | 核占用 | 备注 |
|---|---|---|---|---|
| **A** | 24 | 1 | 24 | **主力**：24 个任务并行，其余 8 个排第二轮 |
| **B** | 12 | 2 | 24 | |
| **C** | 8 | 3 | 24 | |
| **D** | 6 | 4 | 24 | |
| **E** | 3 | 8 | 24 | |
| A′ | 30 | 1 | 30 | **上限对照，不作主力**——2 个任务超订 |
| A″ | 32 | 1 | 32 | 全部 f 任务一次铺开（超订 2，只压边界） |

**先做 A 与 E 两个极端**（24×1 与 3×8）：若差异不大，说明瓶颈在 I/O、矩阵不必做全；若差异大
再补 B/C/D。**A′ 与 A″ 只在想量"超订的代价"时跑**。

**要改的**：

1. **计算单元下沉到 `(batch, ds 组)`，`fengine` 落 tmpfs**（2026-09-29 加，**这是 P3 的第一刀**）
   ——`fengine` 整 batch 是 **67.4 GB**，而 `/dev/shm` 只有 **62 GB**，**装不下**；按 ds 组则
   每组 **16.9 GB**、**能放 3 组**。所以调度粒度必须是 ds 组，`FXCORR_FENGINE_ROOT` 才有意义
2. `run_batch.sh` 的 f 循环（32 个任务）——加并行度参数与**失败语义**：现状是"任一失败即
   `exit 1`、不跑后续站"，并行后须重新定义（建议**跑完全部、收集失败列表再判**，并记清楚
   是哪个失败）
3. `run_batch.sh` 的 x 分片循环（4 个组）——同法处理，量级小但同样是串行

**一个漂亮的吻合**（2026-09-29）：**每组是 8 个 f 任务**（4 站 × 2 ds），而 **tmpfs 装得下 3 组**
（62 ÷ 16.9）——**3 组 × 8 = 24 个任务，正好压满 §10 定的 24 核基准**。所以 P3 的主力配置不是
"32 任务铺满 30 核"，而是"**按 ds 组调度 + 同时 3 组**"：它同时满足了 tmpfs 容量、24 核基准，
和 `v6-plan.md` 的部署形态（计算单元 = `(batch, ds 组)`）。

### 10.1 并行度怎么定（**从配置推导**，2026-09-29 定）

**这一节是给"换到别的节点上跑"用的**——本配置的选定基准只是它的一个实例。

**本配置（4 站 × 8 ds，30 核 / 62 GB tmpfs / 4.2 GB/s）的基准**：

| 项 | 值 | 怎么来的 |
|---|---|---|
| ds 组数 G | **4** | `run_batch.sh:214` 的并查集按**频段重叠跨站**切分；V6 S0 记录"32 datastream / 4 个 ds 组各 8 ds" |
| 每组 f 任务数 | **8** | 4 站 × 2 ds |
| 单组 `fengine` | **16.9 GB** | 整 batch **63 GiB** ÷ 4 |
| **同时组数 N** | **3** | 三个上限取最小，见下表 |
| **并行度** | **24** | N × 每组任务数 |

**N 取三者最小**——三个约束的性质不同，任何一个都可能成为瓶颈：

| 约束 | 上限 | 本配置 |
|---|---|---|
| **tmpfs 容量**（容量，硬墙：超了直接写失败） | `tmpfs ÷ 单组 fengine` | 62 ÷ 16.9 = **3.7 → 3** |
| **CPU**（算力；留余量，节点 30 核取 24） | `可用核数 ÷ 每组任务数` | 24 ÷ 8 = **3** |
| **共享存储带宽**（吞吐） | `实测带宽 ÷ 单任务读速率 ÷ 每组任务数` | 4.2 GB/s ÷ 128.5 MB/s ÷ 8 = **4.1 → 4** |

**取最小 = 3 组 = 24 个任务**。

**换节点/换配置时，重算这四步**：

1. 由 `.input` 定**组数 G**（看频段重叠；脚本里是并查集）
2. **单组 `fengine`** = 整 batch 的 `fengine` ÷ G。整 batch 的量可实测，也可按
   `data-volume.md` §2.1 的 D8 公式先估
3. `N = min( tmpfs ÷ 单组, 可用核 ÷ 每组任务, 实测带宽 ÷ 单任务读速率 ÷ 每组任务 )`
4. **并行度 = N × 每组任务数**

**若算出 N < 1**：单组都放不下 tmpfs——**必须先减小 batch 时长**（`n_subints`）**或上 cf16**
（§15 记的触发条件正是这个），不能指望并行度救。
**若 tmpfs 不是瓶颈**（比如用了本地 NVMe 而非 tmpfs），则 N 由后两条决定——但要注意
`fengine` 落 SATA SSD 会撞 `data-volume.md` §5.1 的 132×。

**判据（自检）**：

- **并行前后 SWIN 逐字节相同**——**门禁**，不通过不算完成（沿用 V3 P3 的逐位全等对拍）
- 单 batch wall **从 235 s 显著下降**；给出 A/B/C/D 的最优解与该解的**核效率**（相对单核
  线性的百分比）
- 每条并行线的**串行残余被定位**（V3 P3 说"受串行 I/O 限制"，这次要说是**哪一段**）

**本阶段顺带完成三个标定**（不单列步骤，它们都是从上面的实测里算出来的）：

| 标定 | 问 | 怎么算 |
|---|---|---|
| **算力** | Q1：30 核实测 TFLOPS | 由最优配置的 wall 反推；换算 **N = 1.7 / X**（追上 4 站 VGOS 实时需几个节点）——**这是 V7 交付的核心数字** |
| **容量** | Q3：tmpfs 放几组、batch 时长上限 | 由 `fengine` 的 tmpfs 峰值实测 |
| **存储** | Q4：`/work2` 撑得住多大并行度 | 由实测带宽代入 §4.3 的分档 |

## 11. P4：mpifxcorr 对照

**用一个节点跑 `run_bench.sh`**，同一份 `raw`。**两条配置各跑一次**：

| 配置 | mpifxcorr NP | fxcorr 任务数 | 判定 |
|---|---|---|---|
| 4 站 × 8 ds（V6 S3 用过的） | **34** | 32 | **核数超订、内存吃紧**——压边界 |
| **2 站 × 8 ds**（t25362 真实规模） | **18** | 16 | **宽裕，且对拍链已建好**（V6 S1：256/256 按 key 全匹配） |

**两条都跑的理由**：4 站是 V6 的可比口径，2 站是能稳跑的口径。**先 2 站（稳），再 4 站压边界**。

### 内存：先纠正一个直觉

**`/dev/shm` 是内存文件系统——fxcorr 落在 tmpfs 里的 `fengine` 就是内存**，不是额外的东西。
所以 mpifxcorr"不落 tmpfs"**不等于"更省内存"**：

| | fxcorr | mpifxcorr |
|---|---|---|
| F 数据在哪 | `/dev/shm` 文件 | 进程堆内存 |
| 占用内存 | **是** | **是** |
| 可控性 | **可控**——分片后 16.8 GB/组、x 消费完即删 | 由 MPI 缓冲深度决定，运行时分配 |
| 单节点占用 | 67.4 GB（不分片） | 上界同为 67.4 GB，**实际未知** |
| 跨节点 | 分片摊到各节点 | 也摊，**但每 batch 要付 ≈65.8 GB/s IB 交换** |

**mpifxcorr 的省内存优势只存在于跨节点场景**（把 F 数据摊到 N 个节点）。**单节点跑时它没有
这个优势**，反而多出 MPI 缓冲与"每进程各持一份"的开销——V6 S3 观察到它 **CPU 是 fxcorr 的
20×**（4276 s vs 210 s），那个开销在内存上同样存在。

**净账**：单节点上 mpifxcorr 的内存**大概率不比 fxcorr 少、可能更多**——但这是推测，
**V6 S3 没记内存峰值，这正是 P4 要补的那一项**。

**两条实打实的风险**：① Slurm 的 `--mem` 超限直接 **OOM kill**，不是变慢——申请时给足；
② 123.5 GiB 减去一个 batch 的 F 数据（上界 67.4 GB）后余量不大。

**判据（自检）**：

- mpifxcorr 产出的 SWIN 与 fxcorr 的一致（V6 S2.5 已验过"新路径 raw 喂 mpifxcorr 结果一致"）
- **wall、CPU、内存峰值**三者落档，两条配置各一份
- 与 V6 S3 的 384 核数字对照，**说明核数从 384 降到 32 对两者的影响是否对称**

## 17. P6：容器化（Singularity）——2026-09-29 加

**为什么加**：目标集群只有 **Singularity 3.8.0**（无 docker / apptainer，P1 建档实测），而 V2 建的
是 **Docker 镜像**。后期要容器封装，这条路必须先跑通；而且 V7 自己就撞出了它的必要性——
**裸机跑时四个根靠默认值，把 `fengine` 落到了共享存储**（测出 899 s/batch），而正确落点是
tmpfs（62 GB，当时完全空闲）。容器化之后这类**隐式默认**更难被发现：容器内的 `<workdir>/fengine`
看起来一样，但它到底落在宿主哪块盘上，不显式声明就说不清。

**做什么**：

1. **镜像来源**：`fxcorr/fxcorr:latest`（V2 单镜像，见 `docker/README.md`）→ `.sif`。
   **由用户手工 `singularity build` 后拷到集群**（2026-09-29 定）——目标集群无 docker，
   在能构建的机器上出 `.sif` 再传，比在集群上拉 registry 稳
2. **四个根显式透传**：`FXCORR_RAW_ROOT` / `_FENGINE_ROOT` / `_VIS_ROOT` / `_PRODUCT_ROOT`。
   与 `data-spec` 的容器约定一致（"各根按宿主同路径可见"，由外部编排保证）；宿主侧
   `fxc()` 现在是 `docker run --rm -v $WORKDIR:$WORKDIR -w $(pwd)`（`run_batch.sh:59`），
   **Singularity 侧要提供对应封装**（`singularity exec --bind`），且 `--bind` 的路径要覆盖
   **四个根而不只是 workdir**——`fengine` 重定向到 `/dev/shm` 时，只挂 workdir 就挂不进去。
   **且 `--bind` 的源路径必须先在宿主上存在**：不存在时 singularity **直接拒绝创建容器**
   （`FATAL: ... mount source ... doesn't exist`），不是警告了事——所以封装里要先
   `mkdir -p` 每个根。**脚本已写**：`/public/home/cstu0036/fxcorr/run_batch_singularity.sh`
   （用法 `<batch_id> <workdir>`，内部处理上面三条；`FXCORR_RUN_MODE=host` 是关键——我们
   **已经在容器里**，`fxc()` 直调才对），已用不存在的 batch 验过链路通到 `run_batch.sh` 的
   前置校验。
3. **与裸机对照**：同一 batch、同一份 raw，跑同样的链

**判据（自检）**：

- 容器内跑出的 **SWIN 与裸机逐字节相同**（回归门禁）
- 容器与裸机的 wall time 差异落档（overhead 有多大）
- **在容器内用 `df` 验证 `fengine` 确实落在 tmpfs 上**（不是共享盘）——这条正是 V7 踩过的坑
