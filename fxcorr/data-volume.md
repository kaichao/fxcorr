## 1. 框架：维度与公式

数据在流水线里同时被两个维度切分。理解任何一个落盘项，都要同时说出它"每多久落一次"和"每次覆盖多宽的频带"。

### 1.1 时间维度（算法级，自细到粗）

| 层 | 定义 | t25362（实测） | test 配置 |
|---|---|---|---|
| 采样 | 1 /(2×band 带宽) | 15.625 ns（64 Ms/s 实采样） | 125 ns（8 Ms/s） |
| **slice** | `stime = 1/specRes`（公共信号网格） | 2 µs（specRes 0.5 MHz） | 2 µs |
| **FFT 块** | `blockns = subintNS / blockspersend`（第 7 节的 `blockns`，亦称 subloop） | **4 µs**（5.12 ms / 1280） | 1.024 ms（0.524288 s / 512） |
| **subint** | `.input` 的 `SUBINT NANOSECONDS`（= DiFX 的 Core 短积分） | **5.12 ms** | 0.524288 s |
| **intTime** | `.input` 的 `INT TIME (SEC)`（= Manager 最终积分） | **1.024 s**（200 subint） | 1.048576 s（2 subint） |
| **batch** | `n_subints × subint`（`batches/<id>.json`） | 11.264 s（t25362 观测）／1.024 s（本文示例） | 2.097 s（默认 4 subint） |

三层术语的对应见 `data-spec.md` 第 12 节的"时间层级"表。

### 1.2 频率维度（自细到粗）

| 层 | 定义 | t25362（实测） | test 配置 |
|---|---|---|---|
| **网格点** | `specRes`，公共信号的最小频率单位 | 0.5 MHz | 0.5 MHz |
| **通道** | `bandwidth / numchannels`（`.sp` / SWIN 的频率分辨率） | 250 kHz（32 MHz / 128 通道） | 0.977 kHz（4 MHz / 4096 通道） |
| **band** | `.input` FREQ TABLE 的一条（`BW (MHZ)`） | 32 MHz × 32 条 | 4 MHz × 1 条 |
| **band 组（一个 datastream）** | 一个 ds 记录的全部 band | 8 band = 256 MHz | 1 band |
| **全站跨度** | `max(freq+bw) − min(freq)`，遍历全部 ds 的全部 band（`commonsignal.cpp` 的 `deriveGrid`）——**只有公共信号覆盖这么宽** | **7072 MHz**（2936.40–9976.40，最高频点 + 32 MHz 带宽） | 4 MHz |

**关键差异**：t25362 的"实际记录带宽"是 1024 MHz（32×32 MHz），但**公共信号要覆盖 7072 MHz 的跨度**——跨度里的间隙照样生成网格点，只是不被任何站读取。这是公共信号体量的唯一决定因素（§5）。

### 1.3 体积公式（**权威定义**，2026-09-21 从 `data-spec.md` 11 节移入）

```
D8（频域谱）  ≈  16×D7（原始基带，2bit 记录）  ≫  D10（可见度，单基线）
D15（公共信号） ≈  16×D7（单站 2bit；float32 复基带 vs 2bit 实基带，与带宽无关）
D10 随基线数 O(N²) 增长，多站大阵可能反超 D7；D11/D12（科学产品）≈ D10 量级
配置类（D1～D6、D9、D13）体积很小（KB～MB）
```

**注意 D8 大于 D7**：`.sp` 是全精度复数落盘（每采样 0.5 个 8 字节 cf32 = 4 B/采样），而 2bit
原始数据只有 0.25 B/采样。mpifxcorr 的 F 数据流式不落盘，落盘体量此前不可见；"频谱域压缩"
实际发生在 D8→D10 的积分折叠。

**通用公式**（单站、单 pol；D7/D8/D10 可精确估算，D11/D12 仅量级）：

| 数据 | 公式 | 说明 |
|---|---|---|
| D7 | `fs × b/8 × nband` | fs = 采样率（样本/s，= 2×band 带宽，由 `data-spec` 5.2 节的帧结构反推）；b = 记录位宽（1/2/8bit）。**`nband` = 每站 recorded band 数，含极化**——**这是最容易算错一处**：t25362 的"32 band"是**频段数**，而它每个频段有 X/Y 两个极化、各占一个 recorded band，所以代入公式的 `nband` 是 **64**；用 32 会**少算整整一半**（2026-09-27 重算时踩到过） |
| ~~D15~~（已取消，V6 S2.5） | `覆盖带宽 × 8B × 时长` | 原"仿真公共信号"目录，**现在只在 `station` 内存中存在**（算全部、留一段）。公式仍成立：float32 复基带（8B/复样本 × 覆盖带宽复采样率），**恒 = 16× 单站 2bit D7**；覆盖带宽 = **全站 band 跨度**（同带多站 = 单站带宽，异带多站放大，见 `data-spec` 5.8 节）；float16 可降 8×（预留） |
| D8 | `(nchan/fftchannels) × fs × 8B × nband` | cf32 = 8B/复数；fftchannels = 2×nchan（50% 重叠）时 = **4×fs×nband**，与 nchan 无关（nchan 增大 → 每 FFT 块采样同比增大 → 块数反比减少，两者抵消）；pcal.bin / autocorr.bin 体积可忽略 |
| D10 | `(74 + 8×nchan) B × nband/intTime × nbaseline` | 每基线每 band 每积分一条 74B 头 + nchan 个 cf32 记录（SWIN 布局见 `data-spec` 5.4）；nbaseline = N(N−1)/2 |
| D11（FITS-IDI） | ≈ 1~2×D10 | difx2fits 把 SWIN 复制进 FITS UV DATA 加表头，同量级、稍大 |
| D12（Mark4） | ≈ D10 | 同量级复制 |

**D7/D8 比例**（50% 重叠 + cf32 前提下，与 nchan、fs 均无关）：`D8/D7 = 32/b`——2bit → 16 倍；
1bit → 32 倍；8bit → 4 倍。只有 ≥32bit 浮点记录（不常用）D7 才反超 D8。

**两个参考实例**（速率口径）：

| 场景 | D7 | D8 | D10 |
|---|---|---|---|
| test 配置（1×4MHz band、2bit、8Ms/s、nchan=4096、intTime 1.048576s） | 2 MB/s/站 | 32 MB/s/站（16×） | 31 KB/s（1 基线）→ 2.7 GB/天 |
| 大阵（N=20、8×32MHz band、2bit、64Ms/s、nchan=2048、intTime 2s） | 128 MB/s/站 → 11 TB/天 | 2 GB/s/站（16×）→ 177 TB/天/站 | 12.5 MB/s（190 基线）→ 1.1 TB/天 |

**三条容量结论**：① `fengine/` 中间数据是 D7 的 16 倍，须按生命周期尽快清理（batch 的 x 完成后
即可删）；② D10 才是真正的"小"数据——单基线时 ≈ D7 的 1/64，但随基线数平方增长，大阵可反超
D7；③ ~~D15 公共信号与 D8 同量级（16× 单站 2bit D7）~~——**已随 V6 S2.5 取消，不再是落盘项**
（生成量仍是这个量级，但只在 `station` 进程内存在）。生命周期与可删时点见 `data-spec` 12 节。

**读这张表的三个要点**：

1. **只有 1 与 3 是"宽频"的**：公共信号覆盖全站跨度，raw 帧覆盖该 ds 的全部 band（1 已不落盘，但生成量不变）。**其余落盘项都是窄频的**（单 band、单 freq 或 tone 列表）——这正是 §5 瓶颈排序里"公共信号覆盖跨度"一项的根据。
2. **越下游粒度越粗**：subint（D8）→ intTime（D10/D11）→ batch（元数据）。**唯一的例外是 D14 的 acc 窗口**，它比 subint 更细。
3. **时间与频率的耦合点只有两处**：D15（每 slice 覆盖全跨度——已不落盘，但生成量与算力代价照旧）与 D7（每帧覆盖该 ds 的全部 band）。这两处的"频率宽度"直接决定体量。

### 2.1 D8 的组成（单 subint 一条记录）

```
i32 scan + i32 sec + i32 ns                     12 B
u32[ceil(blockspersend/30)] valid_flags         每 30 个 FFT 块 1 个字
f32[blockspersend] weights                      每 FFT 块 4 B
cf32[blockspersend × num_channels] spectra      每 FFT 块 × 每通道 8 B   ← 主体
```

t25362 代入（`blockspersend` 1280、`num_channels` 128）：`12 + 43×4 + 1280×4 + 1280×128×8` ≈ **1.32 MB / subint / (ds,band)**。spectra 占 99.6%——weights 与 flags 可忽略。

重叠。**TFLOPS 的绝对值留 S3 标定**——§5.1 的 1.7 TFLOPS 是公式粗估，本表只给可核对的 CPU 时间。

**分片等价性（S1 的判据 1/2）**：两条路径的记录数相同（256 = 4 组 × 64，不漏不重），
**按 key 逐记录全匹配**（`cmp_swin.py --by-key`）；但**文件字节序不同**——分片归并按整数纳秒
重排，顺序与不分片不一致。**这正是判据要求按 key 而不是按字节比的原因。**

### 3.2 S3 规模验证：20 个 batch 端到端（2026-09-28）

**配置**：4 站 × 8 ds（`t25362-4st` 仿真）在 `ssh difx`，每 batch 1.024 s、**20 个连续 batch**
（20.5 s 观测）；数据由 **fxcorr-sim 轻量模式**造（`FXSIM_LIGHT=1`，结构同完整链、数值无物理意义）。

| 阶段 | 实测 | 说明 |
|---|---|---|
| 造数（20 batch、**79 GB**） | **8.6 s** | 轻量模式、`-p 32` |
| 流水线 f + x（20 batch） | **4945 s**，**235 s/batch** | `run_batch.sh`；f 逐站**串行** |
| 每 batch `fengine`（32 ds） | **62.9 GB** | 单 ds 1.97 GB |
| `difx2fits`（20 batch 全量） | **0.53 s** | 产物 FITS 14.5 MB |
| SWIN（20 batch） | 22.5 MB | 1,124,352 B/batch，精确 20 倍 |

**关键结论：当前 wall time 的主因是 f 的串行，不是算力。** `run_batch.sh` 逐站跑 32 个 f
任务；S1 实测同一批任务**并行**（16 路）只用 6.1 s，而这里 32 个串行就是 ≈200 s。**把 f 的
任务并行起来是数量级的差别**，与 §5.1 那句"算力差 3~11×"不是一回事——后者只算 FFT 的 flops，
未计 I/O 与调度。

**外推**（单节点、当前串行行为）：1 小时观测 = 3516 batch ≈ **229.5 小时**；把 f 任务并行
（32 路）后按 S1 的实测比例降一个数量级，再靠多节点分 batch 才是 §5.1 的扩展方式。
**这组数字应取代 §5.1 的纯公式推算。**

**生命周期在真实规模上走通**：fengine 62.9 GB/batch × 20 = 1.26 TB 装不下所在分区（407 GB），
按 `data-spec` 第 12 节"x 消费完即删"逐 batch 清理，**峰值压在单 batch 的 63 GB**。

**mpifxcorr 对照（同一节点、同一份数据、同一个 batch 20）**：

| | mpifxcorr | fxcorr |
|---|---|---|
| 并行单元 | 1 batch 跨 **34 个 MPI 进程** | f 的 **32 个任务并行** + 1 个 x（全量） |
| **wall time** | **120.6 s** | **80.7 s**（f 7.3 + x 73.4） |
| **CPU 时间** | **4276 s**（`user 71m16s`） | **210 s**（137 + 73） |
| `fengine` 落盘 | 0（进程内存 + MPI 交换） | **63 GB**（本地） |
| 跨节点流量 | `fengine` all-to-all | **0** |

**两点要说清**：

1. **对照必须拿"f 并行"的 fxcorr 比**，不能拿 `run_batch.sh` 去比——那条路径逐站串行跑
   32 个 f 任务（235 s/batch），比 mpifxcorr 还慢一倍，但那是脚本的调度方式，不是架构
   限制。**并行后 fxcorr 的 wall time 是 mpifxcorr 的 0.67×**。
2. **CPU 时间差 20×**（4276 s 对 210 s）：mpifxcorr 每个 MPI 进程各持一份数据的开销、
   fxcorr 的 f 只做通道化而 x 只做相关。**这个差异对"多节点并行 batch"的扩展方式更有利**——
   fxcorr 用同样的节点数能跑更多观测。

**本次是单机对照**（difx 一台机器），跨节点流量那一列没有实测——那需要真的跨节点部署。

### 4.1 一个 batch（1.024 s）

按 §1.3 的公式代入，**1.024 s、4 站**（t25362 配置是满速 VGOS，见 §3）：

| 目录 | test 紧凑配置 | **t25362 / VGOS（4 站）** | 驱动因素 |
|---|---|---|---|
| 公共信号（D15 已取消） | 32.8 MB | **57.9 GB** | `8 B × 覆盖跨度 7072 MHz × 1.024 s`，**与站数无关**；S2.5 起**不落盘**，这一列读作各 `station` 任务的**生成量当量** |
| `raw/`（D7） | 8.2 MB | **4.2 GB** | 4 站 × 1.028 GB/s × 1.024 s |
| `fengine/`（D8） | 131 MB | **67.4 GB**（分片后 **16.8 GB / 组**） | = 16 × raw（2bit，推导见下） |
| `vis/`（D10） | 0.19 MB | **0.84 MB** | 96 基线 × 8 freq × 1098 B / 1.024 s |
| `vis-parts/`（D16） | — | ≈ vis | 同一批记录的分片形态（§7.5） |
| `product/`（D11） | ≈ vis | ≈ vis | difx2fits 复制 + 表头 |
| **落盘合计** | **≈ 139 MB** | **≈ 72 GB** | **不含公共信号**（S2.5 起不落盘；含它则 test ≈ 172 MB / t25362 ≈ 129 GB） |

**`vis` 的基线数口径（2026-09-27 订正）**：4 站 = `C(4,2) × 4 频段组 × 4 极化组合` = **96 条**；
2 站是 16 条（`ACTIVE BASELINES: 16` 实测），对应 **0.14 MB**。本表此前用 2 站的 vis 值配 4 站的
其他项，现按 4 站统一——两项相差 5 个数量级，不影响任何结论，但口径要一致。

**`D8 = 16 × D7` 的推导（2026-09-27 补，常被误读）**——不是"4 B/样本"：

```
每个 FFT 块（50% 重叠，fftchannels = 2×nchan = 256）
  输入  256 个 2bit 实样本            = 256 × 0.25 B =   64 B
  输出  nchan=128 个 cf32 复样本      = 128 ×    8 B = 1024 B
  比值  1024 / 64 = 16
```

`cf32` 是**每个复样本 8 B**（实虚各一个 float32），不是 4 B。16 倍 = `(nchan×8) / (fftchannels×0.25)`，
与 `§1.3` 的 `D8/D7 = 32/b`（2bit → 16）一致。**反推核对**（t25362 实测）：每 `(ds, band)` 的
D8 = 257.0 MB/s、D7 = 16.06 MB/s，比值 **16.00** ✓。

**这就是"1 秒数据 129 GB"的来源**（含公共信号；S2.5 起它不落盘，**落盘量降到 ≈ 72 GB**），
也是本地化部署的第一约束。

> **✅ 本节 4.1 / 4.2 的推算已被 S0 实测核对**（2026-09-27，4 站 t25362 参数仿真，两次跑）：
> **体量逐项命中在 0.3% 以内**——公共信号 4 站 1.024 s，推算 57.9 GB / 实测 **57.93 GB**，
> 生成速率 178 MB/s（与跨度无关）。**未命中的是时间**：`station` 端比推算慢 **17×**（读盘
> 跳读放大 221×），这条差异直接催生了 **S2.5**（公共信号改由各站本地合成，不落盘）。
> 各阶段 wall time 与峰值的实测值见 `v6-plan.md` 判据表；S1（真实数据）与 S3（目标规模）
> 的数字回来后回填本表。

### 4.2 1 小时（4 站，同一配置外推 3600 s = 3515.6 个 batch）

**三个口径别混，它们回答三个不同的问题**（2026-09-27 明确）：

1. **累计量**——若整段观测全存下来。`raw`/`fengine` 都是 **TB 级**，但它们

顺序跑一遍生成器（流式 PRNG 做不到"只算自己那段"，`v6-plan.md` S2.5），所以**同样 85% 的
算力白花**——这是方案 E 的固定代价，不是实现缺陷。

## 5. 瓶颈排序

按"压不动"的程度排：

| 序 | 项 | 为什么难 |
|---|---|---|
| 1 | **`fengine` 的汇聚** | 互相关要求"两个站的同一个 freq 同时在场"，x 必须读到全部站的 `.sp`——**物理约束**，只能改格式（cf16）或改 x 的调度模型 |
| 2 | **公共信号的覆盖跨度** | 各 `station` 任务要按**全站跨度**跑一遍生成器（流式 PRNG 做不到"只算自己那段"，`v6-plan.md` S2.5），而真实观测的跨度（6.8 GHz）远大于实际记录带宽（1 GHz）——**利用率仅 14.5%**，且 S2.5 之后这是**算力**而非 I/O 代价（§4.2）。只能减小跨度，或改用 S2 的轻量模式 |
| 3 | `raw` | ∝ 数据率 × 时长，只能靠按 ds/file 分片调度降峰值 |
| 4 | `vis` / `product` | 比前几项小 5 个数量级，**不是瓶颈**；保留成本可忽略 |

**结论**：这是一个"**调参数无效、只能改架构**"的瓶颈——`intTime` 与 batch_id 精度只能改"批次切多大"，改不了"一个批次里 `fengine` 必须同时在场多少"。其他瓶颈（读取正确性、并行度、调度）都能在配置层或脚本层解决，这一个不行。

**但存储不是最终瓶颈**——把 mpifxcorr 与 fxcorr 放在同一套节点上对比后（§5.1），**两者的真瓶颈
都是算力**，存储只是 fxcorr 这一侧必须自己解决的问题（而它可解，见下）。

### 5.1 两种实现的资源对比（mpifxcorr vs fxcorr，2026-09-27 估算）

同一批数据、同一套节点，**两者的算力需求完全相同**（同样的通道化 FFT 与互相关运算），
差别只在**中间数据（D8 `fengine`）怎么走**：

| 维度 | **mpifxcorr**（MPI 一体化） | **fxcorr-f/x**（分片串行） |
|---|---|---|
| 并行单元 | 一个 batch **跨多节点**（MPI 进程网格 D×B） | **多 batch 各占一节点** |
| 读 `raw` | 4.11 GB/s | 4.11 GB/s |
| **`fengine` 落盘** | **0**（进程内存 + MPI 交换，§1.3） | **65.8 GB/s 写**（x 再读 65.8） |
| **跨节点流量** | **`fengine` all-to-all ≈ 65.8 GB/s** | **0** |
| 本地存储峰值 | 无（不落盘） | 67.4 GB（分片后 **16.8 GB/组**） |
| 写 SWIN | 0.82 MB/s | 0.82 MB/s |

**一句话：mpifxcorr 用网络换本地存储，fxcorr 用本地存储换网络。**

4 站 VGOS **实时**（1.024 s 数据在 1.024 s 内处理完）的资源账：

| 资源 | 需求 | 30 核 / 128 GB / 120 GB SSD + IB 节点的供给 | 判定 |
|---|---|---|---|
| **算力** | **≈ 1.7 TFLOPS**（通道化 1.32 + 相关 0.40） | 0.15 ~ 0.6 TFLOPS | **差 3 ~ 11×** |
| 读 `raw` | 4.11 GB/s | 共享存储 25 GB/s | ✓（占 16%） |
| `fengine` 写 → **tmpfs** | 65.8 GB/s | 内存带宽 | ✓ |
| `fengine` 写 → **SATA SSD** | 65.8 GB/s | 0.5 GB/s | **✗ 132×** |
| IB 交换（仅 mpifxcorr） | ≈ 65.8 GB/s | HDR 25 GB/s/口 | **✗ 差 2.6×**，需 NDR 或多口 |

**三条结论**：

1. **两者的真瓶颈都是算力，不是存储**——共享存储 25 GB/s 对读 `raw`（4.11 GB/s）绰绰有余，
   **连 mpifxcorr 都不吃它**（它只读 raw、写 SWIN，`fengine` 不落盘）。**"132×"不能当
   fxcorr 的落地门槛**：那个数字的前提是 `fengine` 落在 SATA SSD 上，而正确部署是落
   **tmpfs**——分片后单组 16.8 GB < 60 GB，写入走内存带宽，约束消失。
2. **`fengine` 落 tmpfs 是 fxcorr 在目标节点上成立的关键**（`FXCORR_FENGINE_ROOT` → `/dev/shm`）。
   4 组并存会到 67.4 GB > 60 GB，所以**同节点要么逐组串行、要么最多 2 组并行**，或者靠
   f/x 流水线化（x 消费完即删）压峰值。**60 GB tmpfs 的意义正在于此**。
3. **换算成节点数**：若单节点实测 0.3 TFLOPS，处理 1 小时观测（需 1.7 TFLOPS 才有实时）
   单节点要 ≈ **5.7 h**；用 N 个节点并行 batch 就是 **5.7/N 小时**——这是 fxcorr 的扩展方式，
   **零跨节点通信**。mpifxcorr 用同一批节点也能加速，但**每个 batch 内要付 ≈ 65.8 GB/s 的
   IB 交换**——这是两者在低配集群上的本质差别，也是 S3 对照要量化的那个数。

> **算力估算的口径**：通道化 = 每 (ds,freq) 502,000 次/s 的 256 点 FFT × 10,240 flops =
> 5.14 GFLOPS，每站 64 个 → 329 GFLOPS/站；相关 = 768 个 (baseline,freq) 对 × 502,000 block/s
> × 128 通道 × 8 flops = 0.40 TFLOPS。**未计内存带宽、OpenMP 效率、I/O 等待**，数量级可信、
> 绝对值待 S3 校准。

> **2026-09-28 订正**：本表原有的 "4+5（cf16 + 流式 x）" 一行写 **1.05 GB / ≈1.6 GB**，是把杠杆 4 误当 8× 之后又乘了一次（1.05 = 8.4÷8、0.53 = 4.2÷8），**该行整体作废**。cf16 是 **2×**（§2.1：spectra 是 cf32、占 D8 的 99.6%，样本宽度 8 B → 4 B）；且**杠杆 5 只降 x 的内存峰值、不降磁盘**，本就进不了这张磁盘体量表。表里另补 §7 分片两行——**分片才是压 `fengine` 的主力**（单组 16.8 GB 已低于 60 GB tmpfs；cf16 的意义是再降到 8.4 GB/组，同节点可放的组数 **3 → 7**）。

**要让本地化真正可行，必须选 4（cf16）或 §7 的按 ds 分片**——零代价的 1 与 2 都压不动 `fengine`（杠杆 1 现在降的是**算力**而非落盘，2 只改持有量），而杠杆 5 只降内存、不降磁盘（§7.2）。**叠加时以分片为主**：分片已把单组压到 16.8 GB，cf16 换来的是同节点并行组数，是否值得动 `.sp` 格式见 §8 第 1 项的触发条件。

## 7. 计算单元的分片（约束与方案，2026-09-26）

### 7.1 目标机的物理约束

计算节点规格（2026-09-27 补全内存）：

| 资源 | 规格 | 对 4 站 t25362 参数意味着 |
|---|---|---|
| CPU | 30 核 | 算力 0.15 ~ 0.6 TFLOPS，**实时需 ≈ 1.7 TFLOPS**（§5.1） |
| 内存 | **128 GB** | 与 tmpfs 共享：tmpfs 最多占 60 GB，进程余 68 GB |
| 本地盘 | 120 GB（SATA SSD，~500 MB/s） | `fengine` 若落此：65.8 GB/s 需求 = **132×**，不可行 |
| 内存盘 | 60 GB（tmpfs，**含在 128 GB 内存内**） | `fengine` 的正解落点——分片后单组 **16.8 GB** 装得下 ✓ |

**结论（2026-09-27 更新）**：不分片时 tmpfs 装不下 67.4 GB 的 `fengine`，机器跑不动——**这正是
分片的直接动因**；分片后单组 16.8 GB 进 tmpfs，且写入走内存带宽、绕开了 SSD 的 132×，
**容量与带宽两个问题一并解决**。剩下的约束是**算力**（单节点差 3 ~ 11×，需多节点并行 batch）
与同节点组数上限（4 组并存 67.4 GB 超出 tmpfs，须逐组串行或最多 2 组并行），见 §5.1。

### 7.2 分片要降的是 `fengine` 的**产生量**

§6 杠杆 5（x 按 freq 组流式）把 x 的**内存**峰值降到 1/nband，但**不减少 `fengine` 的产生量**——`fengine` 是 fxcorr-f 的输出，f 照旧写出该 batch 全部 band 的 `.sp`。当前流程是 f 全跑完才启动 x（`run_batch.sh` 步骤 ④→⑥），所以 `fengine` 的磁盘峰值就是全量。

§6 组合效果表里"4+5 → 1.05 GB"一行成立的前提是 **f 与 x 流水线化**（x 边消费边删，即杠杆 2）；串行流程下这个前提不满足。这台机器的瓶颈是**磁盘占用与写入带宽**，不是 x 的内存——杠杆 5 单独用不够。

**要真正缩小计算单元，f 与 x 都要按同一维度分片**，让每个计算单元只产生、只消费一部分 `fengine`。

### 7.3 分片的自然单位：datastream

取 **datastream**，不是单个 freq。四条边界重合：

| 边界 | 依据 |
|---|---|
| raw | 一路记录线程一个 datastream；`fxcorr-sim` 同构 |
| f 的任务粒度 | 已经是 `(batch, station, ds_index)` |
| zoom band 族 | zoom 子带的父 band 在**同一个 ds 内**（`fxcorr-x/src/main.cpp:239-260`），按 freq 切会切开这个族 |
| fengine 布局 | 目录结构本来就是 `ds_<N>/` |

**按 freq 切不可用**：VDIF 帧内 band 交织（`data-spec` 5.2），读一帧即得到该 ds 的全部 band，只输出一个 band 等于白读其余的——raw I/O 放大 nband 倍。按 ds 切没有这个问题，每个 ds 是一路独立数据流。

**x 侧的分片单位是"一组 ds"（跨站、含全部极化）**，不是单个 ds：互相关要求两站同一 freq 同时在场，且要算全极化组合（RR/LL/RL/LR）。这个组在接口上就是 `ds_group`。

t25362 的实测结构（2026-09-27 读 `.input` 的 DATASTREAM 表）：

| 站 | ds | 频段 | 极化 |
|---|---|---|---|
| BA (tel 0) | 0 / 1 | freq 0-7 | X / Y |
| | 2 / 3 | 8-15 | X / Y |
| | 4 / 5 | 16-23 | X / Y |
| | 6 / 7 | 24-31 | X / Y |
| S6 (tel 1) | 8 / 9 | freq 0-7 | X / Y |
| | 10 / 11 | 8-15 | X / Y |
| | 12 / 13 | 16-23 | X / Y |
| | 14 / 15 | 24-31 | X / Y |

三条要点：

1. **各站的 ds 配置逐位对应**（同数量、同频段、同极化）——这是"跨站成组"能成立的前提，也是"各站 ds 配置相同"这一直觉的实测依据；文件也确实是每站每 ds 一个（`FILE 0/0` … `FILE 15/0`）。
2. **同站内两个 ds 覆盖同一频段、是 X/Y 两个极化**——所以 ds 之间**不是**按频段正交的。**按 ds 序号切会把两个极化拆到不同分片**，baseline 的极化组合算不全。切分单位必须是"频段组"。
3. **分组的最终依据是 BASELINE TABLE，不是 ds 序号**——每条 baseline 条目绑定一对具体的 ds、只出一个极化产品（极化维度被展开进了 baseline 编号）：t25362 的 `BASELINE ENTRIES: 16` = 4 频段组 × 4 种组合（RR/RL/LR/LL），所以 f0-7 组的 `ds_group` = {ds0, ds1, ds8, ds9}，而第 2 条 baseline 是 `(ds1, ds8)` 而非 `(ds1, ds9)`——按序号配对就会配错。机理与实测表见 `data-spec` 第 8 节。

**不同 baseline 之间完全独立计算**（RR/RL/LR/LL 各算各的输入对，无跨极化合并步骤），所以分片**不影响单条 baseline 的结果**；分片只影响**"该分片能算出哪些 baseline"**——一条 baseline 要它声明的两个 ds 同时在场。**在同一 batch 内这不是问题**：该 batch 的 f 任务覆盖该时段**全部站的全部 ds**（f 本就是每 ds 一个任务），所以只要 `ds_group` 按 BASELINE TABLE 正确分组，该频段的 4 条 baseline 就都能算。

**由此 f 与 x 的分片数不同**（这是"任务 ID 不能只有一种形状"的根因）：f 任务 = `(batch, station, ds)`，t25362 是 2×8 = **16 个**；x 分片任务 = `(batch, ds_group)`，t25362 是 **4 组**（每组含 4 个 ds：两站 × 两极化）。`ds_group` 按频段升序编号（0 = 最低频段组）。任务 ID 规范见 `data-spec` 第 6 节。

### 7.4 三条路线

| 路线 | `fengine` 峰值 | x 内存 | 代价 | 本机可行 |
|---|---|---|---|---|
| 不动 | 67.4 GB | 整 batch 常驻 | — | ✗（装不下） |
| §6-4 `.sp` 转 cf16 | **33.7 GB** | 不变 | 改 `.sp` 格式；**与 mpifxcorr 的逐位对拍失效** | ✓ |
| §6-5 x 内部流式 | 67.4 GB（**不降**） | 1/nband | 改 x 调度模型 | ✗（不解决磁盘） |
| **f/x 按 ds 分片 + SWIN 合并**（fxcorr-x `merge` 子命令） | **67.4 / 组数 × 并发**（t25362 组数 = 4 ⇒ **16.8 GB / 组**） | 同左 | 1 中间格式 + 1 子命令 + 1 同步语义（复用 x 已有的 SWIN 写入路径） | ✓ |

最后一条与 cf16 可叠加（**8×**：分片 4 组 × cf16 2 倍 ⇒ **8.4 GB / 组**）——凡涉及 cf16 的倍数都是 **2×**，见 §6 的 2026-09-28 订正。两者的取舍在**对拍**：cf16 改变数值精度，逐位对拍失效；分片只改调度，**逐位对拍保留**。**分片因此是首选**：它单靠自己就把单组压到 60 GB tmpfs 之下，而 cf16 要动格式、要牺牲逐位对拍。

### 7.5 SWIN 分片（`vis-parts/`）与归并写出

分片后每个 x 任务独立产出**局部记录**，落共享盘的 `vis-parts/`；由 **fxcorr-x 的 `merge` 子命令**（同一二进制的另一次调用）按时间归并。做成子命令而非独立程序，是为了复用 x 里已有的 SWIN 写入路径（`visibility.cpp` 的 `writeSWIN`）。**2026-09-28 起分两级**：**batch 级** `merge <batch_id>` 只写 `vis-parts/<batch_id>/merged.part`，**实验级** `merge --experiment` 按各 `merged.part` 的首记录时间定序、才写出正式 SWIN（四条定则见 `data-spec` 5.9 末条）。

**为什么写入必须集中在一处**：SWIN 的追加顺序不是自由的。`difx2fits` 顺序读记录（`DifxVisRecordgetnext` 是唯一读取原语），并按天线检查时间单调——`fitsUV.c:1227` 的 `RecordIsOld()` 把"早于该天线最后一条"的记录判为 old，丢弃后只在结尾打印一行 `out-of-time-range records dropped`（`fitsUV.c:1868`），**不报错**。分片任务各自追加会让时间回退，后写的记录全部静默丢失。**实验级 `merge` 是唯一写入者**，时间单调由它保证——子命令形态不影响这一点：它与分片任务是**不同的进程调用**，分片任务不再写 SWIN。收敛到实验级（而不是"每 batch 完成即写"）是为了多节点：数百节点并行处理不同 batch 时，batch 的**完成**顺序与**时间**顺序无关，**旧形态**（batch 级直写 + 编排层保证同实验串行）在那里静默错数据。

**目录与安全边界**：`vis-parts/` 恒在 `$FXCORR_WORKDIR/` 下，**无独立根**（同 `config/` `batches/` `meta/` 的处理）——分片体积可忽略（SWIN 本体 ≈ 0.14 MB/batch，§4），共享盘毫无压力；**但它必须全局可见**（2026-09-27 补正理由）：多节点部署下**实验级 `merge` 要读跨数百个节点的全部 batch 产物**（`v6-plan.md` S4.1 形态 A），放本地盘就得由编排层逐节点搬运，而 24 h 观测总共才十几 GB（84,375 batch × 0.14 MB ≈ **11.8 GB**）。**靠 `FXCORR_WORKDIR` 指向共享存储实现可见性，不新增根**——它与 `config/`/`batches/`/`meta/` 同类（量小、必须全局一致、独立重定向只有坏处），新增第六个根反而与 P5 的 Q17 定案矛盾。由此外推一条部署硬约束：**`FXCORR_WORKDIR` 整体必须落在全局共享存储上**，本地根只有 `RAW`/`FENGINE` 两个（`SIM_COMMON` 已随 V6 S2.5 取消，公共信号不再落盘）。**必须与 `OUTPUT FILENAME` 目录分开**：difx2fits 的 glob 是 `<job.outputFile>/DIFX*`（`fitsUV.c:82-98`）。放别处即彻底隔离；文件名不用 `DIFX` 前缀是第二重保险。

**归并 key**：SWIN 记录头的时间是 `mjd`(int) + `sec`(double)，浮点相等不可靠。局部记录里存**整数纳秒时间戳**（scan 起点 + `offsetns` 推算），按整数归并，写 SWIN 时再转回 `mjd`/`sec`。

**等待策略**（编排层）：
- **全量**——实验全部 batch 的分片到齐后一次合并。简单、正确，端到端延迟 = 最后一个分片完成时间。shell 测试脚本走这条。
- **增量**——按积分窗口滚动，窗口内分片到齐即写出一段。降低首个结果延迟，但必须显式定义分片迟到时的行为（等 / 超时跳过留空洞 / 告警），否则会变成"看起来在跑、实际卡住"。**明确不做**（`v6-plan.md` S4.2）。

缺片时 **batch 级** `merge` **默认报错退出、不写**；缺 batch 时**实验级**同样。`FXCORR_X_MERGE_FORCE=1` 可强制写出已到齐部分（缺失者静默缺段），两个层级共用这一个逃生口。规范见 `data-spec` 5.9。

**对拍链变成两段**：x 的局部记录 vs mpifxcorr、合并后的 SWIN vs mpifxcorr——分别验，别只比最后那个 SWIN。另：`cmp_swin.py` 现在是**按记录序号逐条比**的，分片/合并后顺序会变，要改成按键匹配（`bl, frq, mjd, sec`）。

### 7.6 取舍：频段维度该不该进 batch 定义（2026-09-27）

**问题**：分片的频段维度应该落在**任务层**（`ds_group` 参数），还是直接落进 **batch 定义**（"每个 (时间段, 频段组) 是一个 batch"）？两者都能拿到"单任务工作集 = 全量的 1/分片数"，差别在**编号体系要不要跟着乘**。

| | **A：batch = 时间段**（现行） | **B：batch = 时间段 × 频段组** |
|---|---|---|
| batch 定义 | 起点 + 时长（频段 = 全部） | 起点 + 时长 + 单个频段组 |
| 频段切分靠 | 任务层 `ds_group` 参数 | batch 本身 |
| `batches/*.json` | 每时间片 1 个 | 每时间片 × 频段组数 |
| 单任务工作集 | 1/分片数 | 1/分片数（**与 A 相同**） |

**B 的诱人之处**：batch 时长可以拉长 N 倍（同样的磁盘预算下），且 batch 是唯一的调度单元、不需要额外的维度。但这两点 A 都能拿到——**时长**由 x 内部流式解决（§7.2 的约束是内存，不是 batch 定义），**调度粒度**由 `ds_group` 参数解决（每个分片任务本来就是独立可调度的单元）。

**B 的代价**：**B/A = 频段组数**（`B 的 batch 数 = 时间段数 × 频段组数`，线性关系）。**与站数无关**——t25362 的 2 站各有 4 个频段组，40 站的配置也是 4 个（各站 ds 配置逐位对应，见 §7.3）。频段组数由 `.input` 的 DATASTREAM 表决定。

以 24 h 观测、1.024 s/batch 为例：

| 项 | A | B（t25362：4 组） | B（极端配置：32 组） |
|---|---|---|---|
| 24 h 的 batch 数 | **84,375** | **337,500** | **2,700,000** |
| `batches/` 下的 JSON 文件数 | 8.4 万 | 33.8 万 | 270 万 |
| 8 位编号能覆盖 | 1185 天 | 296 天 | 37 天 |

**`merge` 的调用次数取决于它按什么粒度调**（2026-09-28 起两级 `merge` 把这个问题分成两问）：**batch 级** `merge <batch_id>` 必按 batch 调、次数 = batch 数（B 模式下也跟着 × 频段组数），产物是 `merged.part`；**实验级** `merge --experiment` 按**实验**调一次（读该实验全部 `merged.part`），与 batch 怎么切无关。所以"×4"那笔代价只落在 batch 级，且它同时把文件数**收敛 4 倍**（4 个 `ds*.part` → 1 个 `merged.part`）。

两条具体的坏处：

1. **`batches/` 被小文件淹没**——极端配置下几百万个 KB 级 JSON 放一个目录，每次调度、每次索引扫描都成瓶颈（t25362 那样的 4 组只是 ×4，不致命，但它没有上限保证）。
2. **迟到阻塞面放大**——分片越细，"某个频段组的 batch 迟到"阻塞整段时间的概率越高（§7.5 的等待策略承受的压力随分片数线性上升）。

**结论**：B **并非不可行**（t25362 只有 ×4 的代价），但**没有必要**——A 用任务层的 `ds_group` 拿到了**完全相同**的单任务工作集，且不引入任何额外对象。选 A 的真正理由是**语义**：

- **batch 回答"哪段时间"**——目录名、编号、生命周期、`batches/` 索引都是时间维度的事；
- **任务回答"这段时间里的哪块频段"**——调度粒度、失败重试范围、资源占用是任务维度的事。

B 把两个维度压进同一个编号后，光看 `batches/` 分不清"这是同一段数据的两个频段"还是"这是两段数据"；而 f 侧本来就按 `(batch, station, ds)` 天然分片，`ds_group` 不需要 batch 配合就能工作。

由此 batch 数只随时间增长（**与站数、频段组数都无关**），8 位编号（10⁸）在 1.024 s 的 batch 下覆盖 1185 天。

**唯一值得重新考虑的情形**：如果将来需要"不同频段在不同时间/不同节点上处理，且各自要有独立的失败重试与状态追踪"——那时频段确实需要一个身份，但那个身份应该是**任务 ID**，不是 `batch_id`（任务 ID 规范见 `data-spec` 第 6 节）。
