## S0：单 batch 端到端实测（V6 第一条，2026-09-27 定，✅ 已完成 2026-09-27）

> 本节与下面 S2.5 节都**保留立项当时的原话**（含已被后续结论取代的表述，如"`sim-common`
> 生成可能是瓶颈"），作为决策档案；**现状以判据表与 S2.5 的改写为准**。

**依据**：文档里**每一个体量数字都是公式推算**（`data-volume.md` §1.3 + §4），推算覆盖不到三处：

1. **`fengine` 的真实文件大小**——公式说"= 16 × raw"，但 `.sp` 是每 subint 一条记录（带
   weights/flags，见 §2.1），实际落盘量与对齐会与公式有偏差。**而它正是分片与 tmpfs 容量的
   唯一依据**；
2. **`sim-common` 的真实落盘量与生成耗时**——D15 是**每 0.5 s 一个块文件**，块数、总字节、
   生成速率都没实测过；
3. **各阶段的 wall time 与峰值**——公式给不出，而"132× SATA SSD""1.7 TFLOPS"这类结论全靠它当地基。

公式的**比例关系**可信（§2.1 的单点推算与实测值精确吻合），但**绝对量与耗时必须实测**。

**配置与机器**：**4 站 × t25362 参数**（32 频段 × 32 MHz、跨度 7072 MHz、intTime 1.024 s）——
与 §4.1 的推算表完全同参才能逐项对照。在 **`ssh difx`**（192 核 / 512 GB / 20 TB）上跑，
测试机装不下（合计 ≈ 129 GB）。

**两次跑（2026-09-27 定）**：

| 次 | 配置 | 目的 | 预期耗时 |
|---|---|---|---|
| **① 流程跑通** | **缩小跨度**（杠杆 1，common 从 57.9 GB 降到 8.4 GB） | 把 `make_testdata.sh` → `run_batch.sh`（**含 `FXCORR_X_SHARD=1` 分片路径**）全链跑通，**先暴露流程问题**——这一步不该被体量问题干扰 | 分钟级 |

## S1：真实规模验证

**依据**：V5 的分片判据（`test/multids/README.md` 判据 7/8/10/11）**全部跑在合成的
4 ds / 4 baseline 小配置上**；t25362 只用到"分组推导与 `data-spec` 第 8 节逐字一致"
（判据 9），**没有在分片模式下跑过全链**。而不分片的 t25362 全链是对拍过的
（`reader-model.md` 4.6 那条 576 条差异的线）。所以"**分片模式在真实规模下与不分片等价**"
这条判据目前是空的——它是 V5 分片改造的验收闭环。

**做法**：两条路径各跑一次 t25362 的一个 batch。

| 路径 | 命令 | 产出 |
|---|---|---|
| 基准（不分片） | `fxcorr-f` × (站, ds) → `fxcorr-x <bid>` | `vis/<exp>.difx/` 全量 SWIN |
| 分片 | 同上 → `fxcorr-x <bid> <g>` × 4 → `fxcorr-x merge <bid>` | 同一个 SWIN |

**判据**：

1. **两条路径的 SWIN 逐记录相等**（`cmp_swin.py --by-key`，多 ds 下记录顺序不对应，
   按 `(baseline, frq, 极化对, 整数纳秒)` 配对）——这是核心判据；
2. **每个 `.part` 的记录数之和 = 全量记录数**（不漏不重）；
3. **顺带记录真实规模数字**：单组 `fengine` 峰值、单任务工作集、x 内存峰值、各阶段 wall
   time，以及**各阶段的 CPU 时间（折算单节点 TFLOPS）**——最后一项是 S3 定节点数最需要的
   量（见 S3 的选型依据），落 `data-volume.md` §3 的参数表。

**t25362 的已知参数**（`data-volume.md` §3/§7.3）：2 站、16 ds、32 band × 32 MHz、
跨度 7072 MHz、每站 1.03 GB/s、1.024 s/batch、**4 个 ds 组**（每组 8 个 ds）。

> **口径订正**：`data-volume.md` §4 的场景表按 **4 站**推算（raw 4.2 GB / fengine 67.4 GB），
> 而 §7.3 的实测是 **2 站 16 ds**。V6 起统一按 **2 站实测**（raw 2.1 GB / fengine 33.7 GB /
> 分片后 8.4 GB 每组）。4 站口径留给 S3 的仿真场景。

## S2：fxcorr-sim 压力测试轻量模式（B2）

**依据**（`v5-plan.md` P6 节）：现状造数走完整频域链（块 IDFT + 帧级三趟 FFT + 条纹旋转 +
pcal），生成速率决定了体量上限；而压测要的是另一类问题——长 batch、多 batch 连续、多站并发、
磁盘边界、长稳不退化。**造数本身不能成为瓶颈。**

**定案（V5 P6 已给，V6 实施）**：跳过物理信号链，**按 band 布局直接填确定性伪随机 2bit
载荷**；帧头、时间轴、band 布局、帧号规则与完整链**完全一致**（复用 `vdifwriter`），种子
驱动可复现。规模由**目标时长 / 目标体量 / 站数 / 频段跨度 / batch 数**给定。

**关键性质：轻量模式不生成公共信号。** 载荷按 `f(seed, station, band)` 直接生成，
不从公共信号派生，也不追求跨站相干（它明确不用于正确性对拍）。**S2.5 之后这一点更重要**
——完整链的 `station` 任务要按**全站跨度**跑一遍生成器（85% 是白算，见 S3 与
`data-volume.md` §4.2），轻量模式把这部分整个省掉。**这条也是 S5 的 B5（按频段组分片
common）被关掉的原因**——见 S5。

**接口**：与病态注入共用一条写入路径（`VDIFWriter::writeFrame` 内按帧号命中，legacy 与
新路径两个调用点自动生效）——这是现有实现的关键性质，V6 沿用。规模参数与病态规则同属
一份处方（B1 的接口），**B2 先做、B1 跟上**（2026-09-27 定）：处方文件是两者的共用接口，
但 S1–S3 的主线只吃 B2。

**实现（2026-09-28）**：环境变量 `FXSIM_LIGHT=1`，只作用于**新路径**（`station` 不带 tone）；
legacy 路径遇到它**报错退出**——那条路径没有可替换的阶段，静默忽略是更坏的选择。规模仍由
`batch.json` 的 `n_subints` 与 `.input` 的帧结构给定（与完整链同口径，逐帧头对拍才有共同
基准）；载荷来自每条 `(station, datastream)` 一个流，种子派生与站噪声同源、band 固定 0
——band 布局是帧的**位置**属性（样本序 % nbands），与载荷内容无关。病态注入
（`FXSIM_GAPS` / `FXSIM_STARTOFFSET`）照常在 `VDIFWriter` 内生效，两模式共用同一份。

**判据**：

1. **与完整链同参数下逐帧头一致**（时间轴、帧号、band 布局），载荷为伪随机——这是"结构
   真实"的定义，也是轻量模式唯一的正确性判据；
2. 同一规模参数跑两次**逐字节相同**（种子驱动）；
3. **生成速率与体量的数字落档**（`v5-plan.md` P6 的验收 6），供 S3 选规模。

## S2.5：取消 D15，公共信号改为节点内生成（方案 E，2026-09-27 定，✅ 已完成 2026-09-28）

**动机是 S0 的实测**（§S0 与 `data-volume.md` §3/§4）。现状的两笔代价都归到 D15 的**落盘形态**上：

| 实测项 | t25362 4 站 1.024 s batch |
|---|---|
| `sim-common` 落盘 | **57.93 GB**（覆盖跨度 7072 MHz，实际只被读 1024 MHz） |
| 生成速率 | 178 MB/s，与跨度无关（mini 183 / full 178） |
| `station` 端读它 | **跳读放大 221×**（读 128 B 跨 28288 B stride）→ 单 ds **34 min**（mini 只需 2 min） |
| 跨节点分发 | 多节点部署下要么各节点重算、要么搬 57.9 GB |

**方案 E：流式生成全部，只保留本 band 段。**

`station` 端不再读 `sim-common` 文件，而是**就地跑一遍公共信号生成器**：PRNG 一路顺序算下去（与落盘路径**完全同一份逻辑、同一个顺序**），每个 slice 算出 `numsamps` 个点后，**只取本 band 的那 `blksize` 个点**交给 IDFT，其余丢弃。

**为什么不是"只生成自己那段"（方案 C，已评估、不可行）**：公共信号由**流式 PRNG** 顺序生成且**跨 slice 连续**（`commonsignal.cpp` 的 `gauss(engine)` 逐点调用）。要拿 slice 内第 `startidx` 个点，必须先把前 `startidx` 个点算出来——每站将付出 2,048,000 slice × 3536 点 = **72 亿个复高斯数**。唯一的出路是把 PRNG 改成可寻址（按 `(slice, freq)` 独立 hash），但那会**改变生成的全部数值**，现有 74+48 个单测与 `gaps/`、`multids/`、`pcal/` 的对拍基准全部作废。**E 绕开了这个前提**：算全部、留一部分，PRNG 一行不改。

**与方案 D 的关系**：D（`sim-common` 按 ds 组切分 + 组内按段连续）比现状省 6.9× 体积、把跳读变顺序读，但它**仍然落盘、仍然要分发**。E 把 I/O 整个去掉，多付的是**算力 ×节点数**（各组并行，wall time 不增）。D 作为 E 未落地时的过渡，不再单独排期。

**性质变化：D15 整体取消**（2026-09-27 定）。频域数据是**中间数据**——它在一个进程内从生成到被消费，没有跨进程、跨节点的生命周期，因此**不该有规范地位**：不设目录、不设根、不进生命周期表、没有清理策略。当初把 D15 列为正式产物，是因为落盘被当成"一次生成摊给多个消费者"的手段；E 把这一步收回进程内之后，D15 就只剩"参数"这一层含义，而参数小到不需要独立目录。

**公共参数只剩一个 `seed`**：`specRes` / `numSamps` / `minStartFreq` 都是 `deriveGrid(.input)` 的**纯函数**（band 频率与带宽的 GCD，`commonsignal.cpp` 的候选筛选），每个节点自己算必然逐位相同，**不必存也不必传**。真正需要跨节点一致的只有 `seed`，它随 `batches/<batch_id>.json` 走即可——那里已经有 `start_mjd`、`n_subints`、`subint_ns` 这批共享参数。

公共信号是 `f(seed, batch)` 的确定性函数，所以"权威单份"从来不是科学必需（`fxcorr-sim-arch.md:75` 自己也承认"确定性复现在科学上等价"），当初选落盘只是**用 I/O 换算力**；S0 的实测证明这笔交易在真实跨度下是亏的。

**代价与边界**：

- 每个节点从头发一遍全跨度：t25362 是 4 个 ds 组 → **4× 算力**。并行承担，wall time 与单次生成同量级（约 5 min，384 核下 32 个 ds 任务同时跑）。
- 内存**不增**：每 slice 一个缓冲即可（`numsamps × 8 B` ≈ 28 KB）。
- **组内重复**：同组 8 个 ds 各自生成一遍（各是独立进程）。若日后成为瓶颈，可把任务粒度改成"一组一进程"，那是另一件事。

**改动清单**：

1. `commonsignal.cpp`：`generate()` 的生成循环抽成**流式 slice 迭代器**（复用同一份 `gauss(engine)` 与谱线逻辑，**PRNG 调用顺序与点数一行不改**）；**落盘路径与 `Reader` 删除**；
2. `main.cpp` / `signalgen.cpp`：`station` 端的数据来源从 `Reader`（读文件）换成该迭代器，**其余处理链一行不动**；
3. `common` 子命令**取消**；无子命令的默认模式改为遍历全部站跑 `station`；`seed` 由 `make_testdata.sh` 传入并写进 `batch.json`；
4. `data-spec`：**5.8 整节删除**；第 2 节目录表、第 3 节数据总表、第 4 节模块 I/O、第 9 节数据流图、第 12 节生命周期表各去掉 D15 相关的一行/一处；
5. `roots.sh` + `fxcorrpath.cpp`：删 `SIM_COMMON` 根——可重定向根从 5 个回到 4 个（`RAW` / `FENGINE` / `VIS` / `PRODUCT`）；
6. `workdir-template/`：删 `sim-common/` 目录与其 README；`data-volume.md` §4/§6 里 common 的列整体重写（从"目录体量"改为"算力"）——**✅ 2026-09-28 补齐**；
7. `fxcorr-sim-arch.md` 的"公共信号模型"与 L75/L111 的决策记录按本节改写。

**判据**：

1. **可行性验证一**：新路径生成的 raw 与现行路径**逐字节相同**（现有 32 个文件即基准；PRNG 顺序不变，变的只是数据来源从"读盘"到"现算"）；
2. **可行性验证二**：新路径产出的 raw 直接喂 **mpifxcorr**，结果与现行路径一致——比 fxcorr 自比对更强的判据；

## S3：规模验证一次

**依据**：`v5-plan.md` P6 的验收 5——"按目标规模生成（小时级 batch 或多站并发），后期流水线
f → x → merge → difx2fits（含容器与编排）全程跑完，记录吞吐、资源占用与磁盘增长"。

**环境**（2026-09-27 定）：

| | 实验环境 | 目标环境 |
|---|---|---|
| 节点 | `ssh difx`：**192 核 / 512 GB 内存 / 20 TB+ 本地 SSD** | **30 核 / 128 GB 内存 / 120 GB SATA SSD / 60 GB tmpfs（含在 128 GB 内）** |
| 网络 | **IB** | IB |
| 节点数 | 1 | **数百** |
| 用途 | 先打通、定标 | 落地形态 |

**用 4 站仿真数据**（2026-09-27 定）：4 站能覆盖"多站并发 + 多 ds 组"两个维度，且比真实
观测可控。走 **S2 的轻量模式**生成。

**要覆盖的维度**（`v5-plan.md` P6 的表）：体量、时长、站数/基线数、通道/band、生成并发、
流水线并发、长稳、磁盘边界。

**规模选型依据（2026-09-27 核算，明细见 `data-volume.md` §5.1）**——4 站 VGOS **实时**
（1.024 s 数据在 1.024 s 内处理完）的资源账：

| 资源 | 需求 | 30 核节点供给 | 判定 |
|---|---|---|---|
| **算力** | **≈ 1.7 TFLOPS**（通道化 1.32 + 相关 0.40） | 0.15 ~ 0.6 TFLOPS | **差 3 ~ 11×** ← **真瓶颈** |
| 读 `raw` | 4.11 GB/s | 共享存储 25 GB/s | ✓（占 16%） |
| `fengine` 写 → **tmpfs** | 65.8 GB/s | 内存带宽 | ✓ |
| `fengine` 写 → SATA SSD | 65.8 GB/s | 0.5 GB/s | ✗ 132×（**故必须 tmpfs**） |
| IB 交换（**仅 mpifxcorr 跨节点**） | ≈ 65.8 GB/s | HDR 25 GB/s/口 | ✗ 差 2.6×，需 NDR 或多口 |

**"1 小时"在 S3 里的含义不是"存得下 1 小时的数据"，而是"用 N 个节点并行 batch 追赶 1 小时的
观测"**。**规模由算力定，不由存储定**：单节点若实测 0.3 TFLOPS，处理 1 小时观测需 ≈ **5.7 h**，
**N 个节点就是 5.7/N 小时**。fxcorr 的扩展是"多 batch 各占一节点"、**零跨节点通信**；mpifxcorr
用同一批节点同样能加速，但**每个 batch 内要付 ≈65.8 GB/s 的 IB 交换**——这正是 S3 对照要
量化的那个数。

**S3 要标定的第一个量是单节点的实际 TFLOPS**（1.7 是公式粗估，未计内存带宽、OpenMP 效率、
I/O 等待），它决定 N，也决定"数百节点"是够用还是吃紧。

**batch 时长上限**（分片后、目标节点）：单组 `fengine` 产生率 **16.8 GB/s**（4 站）→ 60 GB
tmpfs 约 **3.6 s** 占满；而 128 GB 内存里 tmpfs 占走 60 GB、x 还要读该组 `.sp` 进内存，
实际上限更低。**这是 S3 要标定的第二个量。**

**仿真的公共信号从 I/O 墙变成了算力墙**（2026-09-28 改写，S2.5 之后）：D15 取消后不再有
203.7 TB 的落盘，但每个 `station` 任务仍要从头跑一遍全跨度生成器（**算全部、只留自己 band
那段**，流式 PRNG 绕不开，见 S2.5）。按 S2.5 的实测单点外推（7072 MHz 跨度 / 1.024 s batch /
单 ds = **6m01s**，其中 `user 5m39s` = 339 s 纯计算）：t25362 4 站 1 小时 = 3516 batch ×
32 个 ds 任务 × 339 s ≈ **10,600 CPU·小时**，单节点 192 核要 **≈ 55 小时**——比观测时长慢
两个量级。**只有 S2 的轻量模式能绕开它**——理由从"存储"换成了"算力"，结论不变：
这是"B2 是 S3 前置"的量化依据，不是可选项。（数字是外推，S3 实测替换。）

**mpifxcorr 对照**（2026-09-27 定）：在**同一批节点、同一批数据**上跑 mpifxcorr，形成两组
对照：

| | mpifxcorr | fxcorr（分片） |
|---|---|---|
| 并行单元 | **一个 batch 跨多节点**（MPI 进程网格 D×B） | **多 batch 各占一节点** |
| 跨节点流量 | `fengine` 中间数据（该 batch 全量） | 只有最后的 SWIN（KB 级/batch） |
| 单节点资源 | 每进程一份，摊薄 | 全量 `fengine` 落本地（分片后按组） |

mpifxcorr 走"用网络换单节点资源"，fxcorr 走"用本地资源换网络"——**两者之差就是分片架构的
价值**，也是最有力的检验。进程数够：t25362 16 ds → NP = 1 manager + 16 + 1 = 18。
（mpifxcorr 不进镜像、宿主直跑，见 `v5-plan.md` P4 与 `run_bench.sh`。）

**要测的量**：端到端 wall time、跨节点网络流量、单节点磁盘峰值、吞吐（GB 原始数据/小时）、
长稳（连续数小时不退化）。

**进行中的发现（2026-09-28，4 站 × 8 ds 造数一上来就撞到的两件）**：

1. **`run_batch.sh` 的多 datastream 软链缺陷（已修）**：软链重指的源路径写成
   `raw/<st>/<st>_<bid>.vdif`，**缺 `_ds<N>` 后缀**——多 ds 站的文件名带它，于是
   `isfile(src)` 恒假、软链**从不重指**，停在 `make_testdata.sh` 建的最后那个 batch 上。
   后果是 f 按**本 batch 的时间轴**读**另一个 batch 的数据**，两边都不报错，`fxcorr-x`
   照报 "1 integrations written" 而 SWIN 写下 **0 条记录**。**单 batch 场景完全看不出**（软链
   本来就是对的），这正是 `test/multids/` 判据 11 绿着的原因；**真实观测（每站 8 ds）同样会
   中招**——S1 手工跑 f/x 没走 `run_batch.sh`，所以没暴露。修法：按每站 ds 数补后缀，并把
   "源文件不存在"从静默跳过改为**报错**。
2. **`-n > 1` 的 128 ms SUBINT 变体在 4 站配置下让 `fxcorr-x` 写出 0 条记录**（待查）：
   那处 sed 改写是**为 test 配置**写的（0.524288 s 与帧网格不兼容），而 t25362 的 5.12 ms
   **本来就能多 batch**（batch 1.024 s × 16000 fps = 16384 帧，整数，起点也落在帧边界）。
   现象是 x 报 "4 subints, 2 integrations written" 却一条记录都没写。S3 先自备
   `test-sim.input`（内容 = 原版 `.input`）让脚本跳过 sed 来绕开。
3. **`wrap_difx2fits.sh` 指错了 `.calc`，触发 difx2fits 段错误（已修）**：
   `.input` 的 `CALC FILENAME` 被绝对化成 **config 下的原件**，而绝对化了 `IM FILENAME`
   的是 **PRODUCT 下那份**——**没人读那一份**。于是 `D->job->imFile` 停在相对名
   `test_1.im`，difx2fits 按 cwd（PRODUCT）解析找不到 `.im`；而它缺 `.im` 时
   `fitsMC.c` **不查 NULL** 直接索引 `scan->im[antId]` → **段错误**（`fitsML.c` 有
   `if(scan->im)` 保护，所以 ML 那遍只打印一行 "No IM info available" 就跳过，MC 那遍崩）。
   现象是 FITS 写到 51 KB 就断。**上游这个不对称是隐患，但触发它的是我们这边指错文件**：
   修法是让 `CALC FILENAME` 指向 PRODUCT 下那份已绝对化的 `.calc`；修后 FITS 5.4 MB 完整。

**边界（2026-09-27 定）**：编排本身（scalebox）在**其他仓库**，本仓库只交付**规范与程序内

### S4.1 merge 的实验级语义（形态 A，2026-09-27 定，2026-09-28 实施细则定稿）

**现状在多节点下会静默错数据。** V5 实现的是 `fxcorr-x merge <batch_id>` **直接追加写
SWIN**，`run_batch.sh` 的 `FXCORR_X_SHARD=1` 是"逐组跑 + 立刻 merge"。单节点串行 batch 时
正确（时间序天然保证，`usage.md` 原则 2 也要求"同实验的 merge 按 batch 时间序串行"）；
**数百个节点并行处理不同 batch 时失效**：

> 节点 A 处理 batch 5、节点 B 处理 batch 6，B 先完成先 merge 写 SWIN，A 后写 →
> **时间回退** → `difx2fits` 的 `RecordIsOld` 静默丢弃（`data-volume` §7.5，只打一行计数）。

**形态 A：两级 merge，SWIN 的写入收敛到实验级一次。**

```
batch 级（在计算节点本地，跟随 batch 完成）
  fxcorr-x merge <batch_id> [workdir]
      读 vis-parts/<batch_id>/ds*.part，按整数纳秒归并
      写  vis-parts/<batch_id>/merged.part     ← 不碰 SWIN
实验级（全部 batch done 后，一次）
  fxcorr-x merge --experiment [workdir]
      读 全部 batch 的 merged.part（按数据时间序）
      写 vis/<exp>.difx/ 的 SWIN                ← 唯一 SWIN 写入者
```

**定序依据**：实验级 merge 按**各 `merged.part` 的首记录时间**排序，不依赖 batch_id 的
数值顺序（`data-spec` 第 6 节只保证编号由单点分配，没规定"编号 = 时间序"）。若发现
`batch_id` 顺序与时间序不一致，**报错提示**而非静默按其一执行。

**连带**：

- `FXCORR_X_SWIN_CONFLICT`（目标 SWIN 已有本 batch 时间范围的记录即报错）**移交实验级
  merge**——batch 级 merge 不再碰 SWIN，这个防呆只剩实验级一处需要；
- `.part` 的 glob 是 `ds*.part`，与 `merged.part` 不冲突——**命名即隔离**；
- `run_batch.sh` 的分片路径：逐组 + 一次 batch 级 merge（写 `merged.part`）；
  **实验级 merge 不进 `run_batch.sh`**——它是实验级操作，与 `wrap_difx2fits.sh` 同类，
  由编排层在该实验全部 batch 跑完后调一次；
- `usage.md` 的「`merge` 是 SWIN 的唯一写入者」原则**升级为「实验级 `merge` 是 SWIN 的
  唯一写入者」**，batch 级 merge 不再是。

**为什么保留 batch 级 merge**（而不是让实验级直接读全部分片）：24 h 观测按 t25362 参数是
84,375 个 batch × 4 组 = **337,500 个 `.part`**；batch 级归并把文件数收敛 4 倍，且 batch 内的
4 路归并**本来就必须做**——放在 batch 完成时做，失败可只重跑该 batch。

**实施细则（2026-09-28 定稿并实施）**——四条：

1. **实验的认定与 config 来源**：实验级没有 `batch_id`，读不到 `batches/<batch_id>.json`。
   实现扫 `batches/*.json`、**把已有 `merged.part` 的那些 batch 当候选**，用候选的
   `config_file` 构造 `Configuration`（与另外两种模式同一个加载路径）。**候选之间
   `config_file` 不一致即报错**——那说明这个 workdir 混了多个实验，选任何一个都会把 SWIN
   写错；候选为空（还没有任何 batch 做过 batch 级 merge）同样报错退出。
2. **缺 batch 的判据来源：`batches/*.json`，不是 `meta/batches.index`。** 应有集 =
   `config_file` 与本次选定者相同的**全部** batch——`batches/*.json` 是**切批规划**的产物
   （`data-spec` 第 6 节：由单点分配），它就是"这个实验规划了哪些 batch"的权威清单。
   **`batches.index` 是 append-only 的"完成流水"（batch `done` 时才追加），拿它当应有集会让
   `failed` 与未跑的 batch 静默消失、SWIN 缺段且无任何报错**——这正是本文档 S4.2 原措辞的
   漏洞，随之订正。`status` 字段不参与判据（`done`/`failed`/`running` 都仍是"规划过的
   batch"），但会随缺失清单逐条列出，一眼看出是没跑完还是跑挂了。
3. **定序与流式写出**：按各 `merged.part` 的**首记录时间**定序，**不是** `batch_id` 数值序；
   两者不一致时报错而非静默选取。写出**逐个 batch 流式进行**（读一个、批内按整数纳秒排序、
   追加写出、释放），**不做全局排序**——各 batch 的时间范围互不重叠，把 batch 顺序定对就足以
   保证全局时间单调；而全量读入不现实（24 h 观测的 SWIN 约 11.8 GB）。**内存峰值 = 单个
   batch 的记录量**。
4. **根一致性检查：对每个候选 batch 逐个调 `FxcorrPath::checkRoots`，只比 `VIS` 一个根**
   （实验级唯一用到的根）。范围取**候选集而非应有集**——缺 `merged.part` 的 batch 不参与
   写出，检查它没有意义（它本就会触发第 2 条的缺失报错）。这一条与 `run_batch.sh` 的
   `fxcorr_write_roots` 不重复：后者在**写记录时**保证同实验一致，前者拦的是**记录存在、而
   本次运行解析出的根与记录不符**——换了 `FXCORR_VIS_ROOT`、或工作区被两套编排写过。
   `checkRoots` 一致时静默、不一致时打印双方的值并返回 false，所以逐候选检查**没有输出
   代价**——这是选"逐个查"而不是"只查第一个"的理由。

`FXCORR_X_SWIN_CONFLICT` 的移交有个**容易漏的细节**：实验级要查的是**本次将写出的全部 batch
的时间范围**，不是单个 batch 的——否则重跑一次实验级 merge 会追加一整份重复记录。

细则同步写在 `data-spec` 5.9 末条（规范）与 `usage.md` 的 fxcorr-x 节（接口）。

**⚠ 另一处并发缺口（2026-09-27 发现，2026-09-28 核实完毕——下面的表格取代原描述）**：实验级
共享**文本**文件 `PCAL_*` / `SWITCHEDPOWER_*` 同样会被多节点并行写。核实结果与本文档原描述
**不同**（原文写"两者都是 `ios::app` 追加（`visibility.cpp:122`）"——那指向 x 侧那段，而
**x 侧根本不写这两个文件**）：

| 文件 | 真正的写出者 | 打开模式 | 文件名的时间 | 并发后果 |
|---|---|---|---|---|
| `PCAL_*` | **f 侧** `PcalTextWriter`（`applications/fxcorr-f/src/pcaltextwriter.cpp:248`） | **`ios::trunc` 整文件重写**（read-modify-write；幂等重写是 P0 为单机串行设计的策略） | 实验起点 | **竞态丢行**——不是行序问题 |
| `SWITCHEDPOWER_*` | **f 侧** `SwitchedPower`（`libraries/fxcorrcommon/src/switchedpower.cpp:74`） | `ios::app` 追加 | 实验起点 + **ds 序号**（文件名尾） | 行序可能不等于时间序，**不丢** |

x 侧 `visibility.cpp` 那两处 PCAL 代码（`:121` 建文件、`:1072` 写行）**实际不产出任何行**：写行那处
由 `if(nonzero)` 门控，而 `nonzero` 来自 `results` 的 pcal 段——**x 侧从不填充那一段**（pcal 是
f 侧 Mode 算的，x 只做互相关）。这与 `test/pcal/README.md` 的"PCAL 与 mpifxcorr 基准逐字节
一致"互洽：mpifxcorr 的 PCAL 由 manager 写一次，若 x 也写就会是两份、对拍必挂。

**所以 PCAL 的并发缺陷比原描述严重**：`PcalTextWriter::flush` 是"读入整个文件 → 替换本
`(ds, intTime)` 的行 → `ios::trunc` 重写"，两个进程并发时**后写者会丢掉先写者新增的行**——
这是**数据丢失**，不是原文说的"行序不对、短行不会截断"（那套 `O_APPEND`/`PIPE_BUF` 分析对
`ios::app` 的 `SWITCHEDPOWER_*` 成立，对 `PCAL_*` 不成立）。而 **difx2fits 确实读 PCAL**
（`fitsPH.c` 出 FITS 的 PC 表），丢行会影响产物。

**这条不阻塞 S4.1**：形态 A 只改 SWIN 的写出路径，而 SWIN（x 写）与这两个文件（f 写）由不同
程序产出、互不干涉——**形态 A 既不引入也不解决它**。它需要独立处置（给 `PCAL_*` 的
read-modify-write 加锁，或改成"只追加本 ds 的行"从而退化为 `SWITCHEDPOWER_*` 那种形态），
是单独一条的工作量，登记在 S5。

### S4.2 `vis-parts/` 的清理时机与分片迟到策略

**清理时机**（规范，编排层实现）：实验级 merge 成功写出 SWIN 后，该实验的
`vis-parts/<batch_id>/` **整目录**（含 `ds*.part` 与 `merged.part`）即可删——**重跑代价低**
（重跑该 batch 的 x 分片 + batch 级 merge 即可，**不需要重生成 raw**）。`data-spec` 5.9 末条
与第 12 节的生命周期表已写这一行。

**分片迟到策略**（规范）：形态 A 是**全量等待**——实验级 merge 等全部 batch 的
`merged.part` 到齐。**缺失的判据来源是 `batches/*.json`**（2026-09-28 订正：此处原写
`meta/batches.index`，那是 append-only 的"完成流水"、只在 batch `done` 时追加，用它当应有集
会让 `failed` 与未跑的 batch **静默消失**、SWIN 缺段而无任何报错；`batches/*.json` 才是切批
规划的权威清单——理由见 S4.1 实施细则第 2 条）；缺 batch 时**默认报错退出、不写**，
`FXCORR_X_MERGE_FORCE=1` 语义沿用（强制写出已到齐部分 + stderr 列明缺了哪些 batch）。

**增量合并明确不做**（2026-09-27 定）：滚动窗口合并（按积分窗口边跑边出）需要定义"分片
迟到时等 / 超时跳过 / 告警"，这套语义没有真实需求驱动时引入只会变成"看起来在跑、实际卡住"
（`data-volume` §7.5 的原文警告）。将来若首个结果的可见延迟成为真实痛点，再立条目。

## 多节点部署形态（2026-09-27 定）

### 计算单元 = (batch, ds 组)

**不可绕的约束**：x 要"两个站的同一 freq 同时在场"（`data-volume` §5 的物理约束，也是
`fengine` 汇聚地板的来源）。所以**一个 ds 组涉及的全部站的全部 ds 必须在同一节点**。

**粒度由 V5 的分片给出**（2026-09-27 修订）：分片之前说的是"整个 batch 同节点"，分片之后
细化为 **`(batch, ds 组)`**——**一个 batch 的多个 ds 组可以分散在多个节点上并行**，这正是
"数百节点并行同一实验"的实现方式。**并行维度是 `(batch, ds 组)`，不是单个站**：基线要求
跨站，按站切就得跨节点汇聚 `fengine`（代价见 `data-volume.md` §5.1 的对比）。

**f 与 x 同节点**这条不变——同一 ds 组的 f 任务与 x 任务必须同节点。

数百节点 × 每节点若干 batch：节点数上去了，**同实验 batch 的串行约定（路线 B）随之失效**
——这正是 S4.1 形态 A 要解决的问题。

### 数据放置

| 数据 | 谁写 → 谁读 | 本地 / 共享 |
|---|---|---|
| `raw/`（D7） | 记录节点 / 仿真 → 该站 f 任务 | **本地即可**（同 batch 同节点） |
| `fengine/`（D8） | f → 同节点 x | **本地 tmpfs**（`/dev/shm`，见下） |
| `vis-parts/`（D16） | x 分片 → batch 级 merge | **必须全局**（见下） |
| `vis/`（D10） | 实验级 merge → difx2fits | **必须全局** |
| `product/`（D11） | `wrap_difx2fits.sh` → 下游 | **必须全局** |
| `config/` `batches/` `meta/` | 编排 → 各程序 | **必须全局** |

**`fengine` 必须落 tmpfs**（2026-09-27 定，论证见 `data-volume.md` §5.1）：它的产生率是
**65.8 GB/s**（4 站），SATA SSD 只有 ~0.5 GB/s——**差 132 倍**。落 tmpfs 后走内存带宽，该约束
消失；而 60 GB tmpfs 正好装得下**分片后单组的 16.8 GB**。

**同节点组数上限**：4 组并存 = 67.4 GB > 60 GB tmpfs，所以**要么逐组串行、要么最多 2 组并行**，
或靠 f/x 流水线化（x 消费完即删）压峰值。这个上限与 batch 时长上限是同一件事的两面
（见 S3 要标定的第二个量）。

**`vis-parts/` 必须全局共享**（2026-09-27 定；`data-volume` §7.5 与 `data-spec` 5.9 的
"无独立根"定案不变，但**理由要从单节点口径改写**）：

- 形态 A 的实验级 merge 要读**跨数百个节点的全部 batch 产物**——放本地盘就得由编排层逐节点
  搬运，而**总共才十几 GB**（24 h 观测 / t25362 参数：84,375 batch × 0.14 MB ≈ **11.8 GB**）；
- 体积与 SWIN 同量级（`.part` 就是 SWIN 记录流），对共享盘毫无压力；
- **不新增根**（2026-09-27 定）：它与 `config/` `batches/` `meta/` 同类——量小、必须全局
  一致可见、独立重定向只有坏处。**多节点时靠 `FXCORR_WORKDIR` 指向共享存储实现可见性**，
  这与 P5 的 Q17 定案一致（新增第六个根反而与之矛盾）。

**由此推出一条部署硬约束**：`FXCORR_WORKDIR`（含 `config/` `batches/` `meta/` `vis-parts/`）
**必须落在全局共享存储上**；`FXCORR_RAW_ROOT` / `FXCORR_FENGINE_ROOT` 才指向
节点本地盘（D15 已随 S2.5 取消，不再有第三个本地根）。**这正是 P5 根变量化设计要的形状**
——不改代码，只改环境变量。

### 网络

IB。跨节点流量只有两处：**输入数据进节点**（真实观测：raw 从记录节点搬到计算节点）与
**产物出节点**（`.part` → 共享盘，十几 GB/实验）。`fengine` **不出节点**——这是分片架构
相对 mpifxcorr 的本质差别（S3 的对照要量化它）。
